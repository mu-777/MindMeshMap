# 整列アルゴリズムの評価環境（Layout Lab）

整列（Align）アルゴリズムを**測れる状態**にするための道具立て。新しいアルゴリズムを作る／既存を
改善するときに、「良くなったのか」を毎回「なんとなく」で判断しないための土台。

- アルゴリズムそのものの設計・検討経緯 → [align-branch-layout.md](./align-branch-layout.md)
- レイアウトという分野の教科書的な地図 → [graph-drawing-primer.md](./graph-drawing-primer.md)
- 先行研究・先行事例 → [layout-prior-art.md](./layout-prior-art.md)
- E2Eテスト全体の手順 → [testing.md](./testing.md)

## 設計方針（なぜこの形なのか）

### 1. 接続パターンは「列挙」せず「軸」で生成する

「あり得るノードの接続パターンを一通り洗い出す」というやり方は、原理的に終わらない。接続パターンの
空間は無限（任意のグラフ）で、手で列挙したリストは**列挙した範囲でだけ良いアルゴリズム**を生む。
実際、いま壊れやすいのは素朴な列挙では出てこない組み合わせのほう（align-branch-layout.md が
「残る制限」として挙げている「cross群のサブツリーがさらに深い階層で forward側の孫と近接する」等）。

そこで、この問題設定を特徴づける**直交する軸**を決め、その軸上でケースを機械的に生成する
（軸の一覧は下記／実装は `e2e/lib/layout-cases.mjs` 冒頭）。

### 2. ケースごとの「正解座標」は書かない

パターンごとに期待座標や期待順序を書くと、アルゴリズムを触るたびに全書き直しになり、しかも
**期待値自体の誤りを誰も検知できない**（[testing.md](./testing.md) の「流儀」に、誤った期待値が
コメントに書かれていても検知されなかった実例がある）。代わりに3層に分ける:

| 層 | 中身 | 合否 | 実装 |
|---|---|---|---|
| **不変条件** | 破れていたら壊れている、と言い切れるもの（ノードが重ならない／ハンドルの向きどおり／座標が有限／決定的） | 失敗にする（アルゴリズムごとの契約に基づく） | `checkInvariants()` |
| **スコア** | 良し悪しの比較用の数値（交差数・面積・移動量など） | 失敗にしない。比較と回帰検知に使う | `computeMetrics()` |
| **目視** | 最終判断。人間が見るしかない | — | コンタクトシート（SVG） |

### 3. 検出器そのものを疑う

指標が壊れて常に0を返すと、以降のすべてのチェックが「見せかけのOK」になる。実際この環境の
初版で、Liang-Barskyの符号ミスにより**エッジのノード貫通が常に0件**だった（全アルゴリズムが
「貫通0で優秀」に見えていた）。そのため `e2e/layout-quality.mjs` の先頭で、わざと壊した配置を
食わせて各検出器が実際に反応することを毎回確認している（陽性確認・陰性確認）。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `e2e/lib/ts-loader.mjs` | src配下の`.ts`を素のNodeから直接importするためのESMローダー登録（esbuild）。**動的import必須** |
| `e2e/lib/layout-metrics.mjs` | 不変条件チェック＋スコア指標。幾何計算はすべてここ |
| `e2e/lib/layout-cases.mjs` | ケースコーパス（軸に沿った生成＋実マップの取り込み） |
| `e2e/layout-quality.mjs` | 回帰テスト。`npm run test:e2e` に自動で含まれる |
| `scripts/layout-contact-sheet.mjs` | コンタクトシート（SVG）生成＋採点表の出力＋`scores.json` 書き出し |
| `e2e/fixtures/maps/` | 実マップのフィクスチャ置き場（エクスポートしたJSONを置くだけで取り込まれる） |

`e2e/lib/` はテスト本体ではないので、`e2e/run-all.mjs` のテスト探索（`e2e/*.mjs`）には引っかからない。

## 使い方

```bash
# コンタクトシート＋採点表（ブラウザ・devサーバ不要）
npm run layout:sheet
# → layout-lab-out/index.html をブラウザで開くと全ケースを一望できる（git管理外）

# 一部のケース・アルゴリズムだけ／規模ケースも含める
node scripts/layout-contact-sheet.mjs --cases=b- --algorithms=sugiyama-ext,branch
node scripts/layout-contact-sheet.mjs --scale

# 回帰テストとして実行（他のE2Eと一緒に走る）
node e2e/layout-quality.mjs
```

コンタクトシートの見方: 行＝ケース、列＝アルゴリズム。**行内のセルは同じ縮尺**で描くので、
どれがコンパクトかが見た目で分かる。赤枠＝ノードの重なり、赤線＝ハンドルの向きと逆、
橙線＝ノードを貫通するエッジ、右下＝主要スコア。

改善の前後を比べるときは、変更前に `--out=/tmp/before` で `scores.json` を退避してから
変更後の値と突き合わせる。

## ケースの軸

| 軸 | 内容 | 意図 |
|---|---|---|
| **A. ハンドル組み合わせ** | right/left/top/bottom の非空部分集合15通り＋子数1/5＋DOWN方向＋ハンドル無し（旧データ） | 方向混在レイアウトの基本形を網羅する |
| **B. 深さ・非対称** | 直鎖4段／非対称な兄弟サブツリー／cross子がさらにforward子を持つ／方向が交互／同一層に兄弟6つ | 再帰合成・箱サイズ計算の穴 |
| **C. グラフ性** | 複数親・深さの違う合流・純粋な循環・ルート配下の循環・相互リンク・自己ループ・森＋孤立ノード・枝をまたぐリンク | 木でないグラフでの堅牢性（このアプリの主題） |
| **D. サイズ** | 背の高いノード／幅の大きく違うノード／ばらばら | 実測サイズを考慮しているか |
| **E. 初期位置** | 整列済み／ランダム／1点に潰れている／上下反転／配列順のみシャッフル | **差分安定なアルゴリズムでは初期位置も入力**。同じグラフでも別ケースになる |
| **F. 規模** | 50・150ノードのランダム木（`--scale`） | 実行時間とスケール時の破綻 |
| **G. 実マップ** | デフォルトマップ＋`e2e/fixtures/maps/*.json` | 合成ケースだけでは現実の形から外れるため |

**「選択ノードのみの部分整列」を軸に入れていない理由**: `useAutoLayout.applyLayout` の実装上、
部分整列は「選択ノードと両端が選択内に収まるエッジだけの部分グラフを整列し、結果を平行移動する」
処理なので、アルゴリズムから見れば通常のケースと完全に同一だから（平行移動はアルゴリズムの外側）。

## スコア指標

| 指標 | 良い方向 | 意味 |
|---|---|---|
| 重なりノード対 / 重なり面積 | 低 | ノード矩形どうしの重なり。読めなくなる最悪の破綻 |
| ハンドル向き不一致 | 低 | 「rightハンドルに繋いだ子が親の右にいるか」。後述の曖昧さ除外を適用した件数 |
| エッジ交差 | 低 | 美的基準の中で読みやすさへの寄与が最も大きいとされる（graph-drawing-primer.md §2） |
| エッジのノード貫通 | 低 | 無関係なノードの上をエッジが通る。交差と別に効く「汚さ」 |
| 描画面積 / 縦横比 / 充填率 | 低/低/高 | 一覧性。詰めすぎも読みにくいので単独では判断材料にならない |
| エッジ長ばらつき | 低 | 変動係数。揃っているほど整って見える |
| 平均移動量 / 最大移動量 | 低 | メンタルマップ保持（decisions.md §26）。整列前からどれだけ動いたか |
| 兄弟順の反転率 | 低 | 同じ親・同じハンドルの子の並び順が保たれたか |
| 実行時間 | 低 | 整列は編集のたびに走る |

### ハンドル向きの「曖昧さ除外」

整列アルゴリズムはどれも、循環エッジと複数親の非採用側を位置計算から除外する。**どちらの親を
採用するかはアルゴリズムごとに違う**（branchはBFS、sugiyama-extは最深レイヤ）ため、全エッジに
向きの期待を課すと不公平になる。そこで「targetの入次数が1、かつDFSの後退辺でない」＝どの
アルゴリズムでも必ず木エッジになるものだけを対象にしている（`unambiguousTreeEdges()`）。

### エッジ形状の近似

実描画はReact Flowのベジェ曲線（`CustomEdge.tsx`）だが、交差・貫通の判定は**ハンドル位置どうしを
結ぶ直線**で近似している。曲線の膨らみぶんの誤差は出るが、決定的・高速で、同じ近似を全アルゴリズムへ
一様に適用するため相対比較には十分。コンタクトシートの描画側だけはベジェで描いている。

## アルゴリズムごとの契約（どの違反を失敗にするか）

`e2e/layout-quality.mjs` の `CONTRACTS`。ここに無い違反は「そのアルゴリズムが保証していないもの」
として、失敗にはせず件数だけを集計・表示する。

| アルゴリズム | 契約 | 理由 |
|---|---|---|
| `uniform` | ノード重なり無し | ELKに丸投げなので重ならない。ELKのspacing設定が壊れたときの回帰検知になる |
| `branch` | （なし） | クロスバケットの重なりが設計上の既知の制限（align-branch-layout.md 方針A） |
| `flat-axis` | （なし） | x/yを別々の最適化結果から寄せ集める軽量ベースライン。重なりも向きも保証しない |
| `sugiyama-ext` | ノード重なり無し・ハンドル向き一致 | 本番の既定。この2つがこのアルゴリズムの存在理由そのもの |

全アルゴリズム共通の契約: 全ノードの座標が返る／座標が有限／**2回実行して完全一致（決定性）**／
スコアがNaNにならない。

## 現時点の測定結果（2026-07、43ケース×4アルゴリズム、`--scale` 込み）

| 指標（合算） | uniform | branch | flat-axis | sugiyama-ext |
|---|---|---|---|---|
| 重なりノード対 | **0** | 48 | 68 | **0** |
| ハンドル向き不一致 | 43 | 9 | 59 | **0** |
| エッジ交差 | 802 | 40 | 753 | **2** |
| エッジのノード貫通 | 188 | 164 | 523 | **46** |
| 描画面積(千px²) | 32483 | 30307 | **21881** | 24813 |
| 充填率 | 0.394 | 0.388 | 0.439 | **0.456** |
| 平均移動量 | 380 | **148** | 285 | 164 |
| 兄弟順の反転率 | 0.006 | 0.029 | **0.000** | 0.013 |
| 実行時間(ms) | 414 | 1209 | 525 | **8** |

読み取れること:

- **`sugiyama-ext` の暫定採用は数値でも支持される**。重なり0・向き不一致0・交差ほぼ0を、
  他の3つより桁違いに速く（ELK非依存の同期実装。150ノードで2ms 対 uniform 52ms / branch 474ms）
  達成している。面積・移動量でも最良ではないが
  上位で、明確な弱点が見当たらない。align-branch-layout.md「今後の運び」の最終決定を下せる材料は
  揃っている（＝不採用3つのコード削除に進める）。
- **残る弱点は「エッジのノード貫通」**。sugiyama-extは重なり0なのに貫通46件ある。cross群を親の
  primary帯に被せて置く設計上、エッジが他のノードの上を通りやすい。**新アルゴリズム／改善を
  考えるなら、ここが最も伸びしろのある指標**。
- `branch` は移動量が最小（メンタルマップ保持は最良）で交差も少ないが、重なりと実行時間で負ける。
  ノードごとにELKを呼ぶ再帰構造のため規模に弱い（50ノード137ms → 150ノード474ms）。
- `flat-axis` は面積・兄弟順では良いが、重なり・貫通が突出して多い。設計どおりの結果で、
  「方針Aの複雑さが見合うかを測るベースライン」としての役目は果たしている。

## 拡張のしかた

- **ケースを足す**: `e2e/lib/layout-cases.mjs` の該当グループ関数に追加する。既存の軸に収まらない
  ものを足すときは、まず「それはどの軸か」を考える（軸が増えるなら冒頭のコメントと本ドキュメントの
  表も更新する）。
- **実マップを足す**: エクスポートしたJSONを `e2e/fixtures/maps/` に置くだけ。**いちばん費用対効果が
  高い追加**（同ディレクトリのREADME参照。個人的な内容を置かないこと）。
- **指標を足す**: `computeMetrics()` に計算を足し、`METRIC_DEFS` に定義（良い方向・桁数）を足す。
  **必ず `e2e/layout-quality.mjs` に陽性確認・陰性確認を書く**こと。
- **契約を足す**: 改善によって新しい保証ができたら `CONTRACTS` に追加し、上の表にも理由を書く。

## 既知の限界・未実装

- **ランダムファズが未実装**。軸に沿って生成しても、列挙しきれない組み合わせは残る。次の一手として、
  軸上でシード付きランダムにグラフを生成し、不変条件だけを検証して、違反したケースをJSONとして
  `e2e/fixtures/maps/` に昇格させる仕組みを想定している（人力に頼らず未知のパターンを拾うため）。
- **スコアのベースライン比較が手動**。`scores.json` を退避して手で見比べる形。前回値との自動比較
  （閾値超えで警告）はまだ無い。
- **スコアの重み付けは無い**。総合点を1つの数値に畳み込むと、その重みが人の好みと合っているかを
  別途検証しなければならなくなるため、意図的に指標を並べたままにしている。パラメータ自動探索
  （`CROSS_OVERLAP_RATIO` 等の総当たり最適化）に進む場合は、まず重みが妥当かを目視で確認すること。
- **エッジラベルを考慮していない**。ラベル付きエッジは実際には中央付近を占有するが、指標には入れていない。
