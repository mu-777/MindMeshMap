## 背景・課題

[decisions.md §26](./decisions.md) で整列（Align）をELKのINTERACTIVE戦略に切り替え、差分的な安定性を確保した。
その後の議論で次の課題が出た:

> ノードの右側についている子ノードと、下側についている子ノードを分けてAlignできないか。
> 今は全エッジが単一方向（DOWN/RIGHT）で流し込まれるため、下ハンドルに繋いだ子でも右方向の階層に配置され、
> エッジだけが下から出て横に曲がる、という見た目と実際の接続位置の食い違いが起きる。

調査の結果、**必要なデータは既に揃っている**ことが分かった。`MapEdge.sourceHandle`（`'top'|'bottom'|'left'|'right'`）に、
そのエッジがノードのどちら側から出ているかが保存済みで（[types/index.ts](../src/types/index.ts)）、ドラッグでの接続
（[MindMapCanvas.tsx](../src/components/Editor/MindMapCanvas.tsx) の `onConnect`）もキーボードでの子ノード作成
（[useNodeCreation.ts](../src/hooks/useNodeCreation.ts) の `createChildNode`）も、このハンドル情報を必ず記録している。
つまりスキーマ変更・データ移行は不要で、**純粋にアルゴリズムの問題**。

分類ルール（ユーザー確認済み）:

- `sourceHandle` が `right`/`left` → **横系（horizontal）**
- `sourceHandle` が `bottom`/`top` → **縦系（vertical）**
- `sourceHandle` が無い（旧データ等） → マップの `layoutDirection` にフォールバック（RIGHT→横系、DOWN→縦系）

ただし実際の配置方向（ELKに渡す `elk.direction`）は横系/縦系の2値ではなく、`right`/`left`/`bottom`/`top` の4方向を
そのまま使う。右子は右へ、左子は左へ伸ばす（後述「検討した設計方針」のXMind・yFilesの実例を参照）。

## 制約: ELKは1回の実行につき1方向

`elk.direction` はレイアウト実行単位のオプションで、エッジ単位・ノード単位で個別方向を指定する仕組みはELKに無い。
ELK自身が持つ入れ子グラフ機能（`elk.hierarchyHandling`）で解決できないか確認したところ、次の制約が判明した:

- `hierarchyHandling: SEPARATE_CHILDREN` — 階層レベルごとに独立したレイアウト実行になるが、結局「どの実行をどう合成するか」を呼び出し側が自分で組む必要があり、後述の「手動再帰合成」と同じ作業が要る。
- `hierarchyHandling: INCLUDE_CHILDREN` — 全階層を1回のレイアウト実行で処理するが、**`elk.direction` は階層開始ノードの設定のみが有効**で、子孫ごとに異なる方向を混在させることはできない。この制約はELK本体のリポジトリでも既知の未解決課題として報告されている（[kieler/elkjs#26](https://github.com/kieler/elkjs/issues/26)、「親と子で異なるelk.directionを持たせつつ階層をまたぐエッジも扱えるか」という2018年の質問に対し、現状はできない旨の議論がある）。

つまり **ELKの入れ子グラフ機能に乗るだけでは要件を満たせない**。「ELKを部分グラフ単位で繰り返し呼び、結果を手動で合成する」方式が必要、という結論は消去法ではなく実測に基づく。

## 複数親（multi-parent）の扱い

自由描画のグラフなので、1ノードが複数の親から接続されるケースがある（右エッジの親と下エッジの親を両方持つ、等）。
両方の親のブランチに同時に属することはできない（位置は1つしか持てない）ため、どちらか一方を「主たる親」として選ぶ必要がある。

**採用ルール**: 入次数0のノード（複数あれば `nodes` 配列順）を起点に**BFS**で全ノードを辿り、各ノードについて
**最初に発見された経路の親**を主たる親として採用する（= 通常のBFS全域木構築）。BFSはノード配列順・エッジ配列順を
決定的に使うため、同じデータに対しては常に同じ結果になる。主たる親に選ばれなかった側の接続（循環エッジ、複数親の
もう一方）は「追加エッジ」として扱い、**位置計算には使わないが描画は今まで通り**（既存のELK循環処理が循環エッジを
位置計算から実質除外しつつ描画は残すのと同じ扱い方の一般化）。

この「配列順で最初に見つかった方を採用する」という規則は、過去に一度[似た規則が暗黙的で分かりにくいとして修正された
（decisions.md §25）](./decisions.md)ことがあるため、ここでは意図的なルールとして明記する。より賢いタイブレーク
（例: 現在位置に幾何学的に近い方の親を優先する等）も考えられるが、まずはこのシンプルな規則で様子を見る。

入次数0のノードが存在しない孤立した循環コンポーネント（そのコンポーネント内の全ノードが入次数1以上）は、BFSの入口が
無いため、そのコンポーネント内で最初に見つかったノード（`nodes` 配列順）を仮の起点として扱う。

## 実装方針の詳細

> **各方式の計算手順そのもの（フェーズ単位の具体的な処理・データ構造・式）は
> [align-algorithms.md](./align-algorithms.md)（詳細仕様）に一本化してある。**
> ここには「なぜそうしたか」「何を保証しないか」「次にどこを触るか」だけを書く。

### 方針A: `branch`（`src/utils/branchLayout.ts`）

子をハンドル別に4方向のバケットへ分け、子孫を先に再帰でレイアウトして「サイズの確定した箱」にしてから、
バケットの向きに対応するELK方向で1回ずつ配置して合成する（Eades & Feng方式）。低レベル関数 `runElkLayout` を
`uniform` と共有するため、§26で確立した差分安定性をそのまま引き継ぐ。
手順の詳細は [align-algorithms.md](./align-algorithms.md) §2。

**既知の制限（クロスバケットの重なり）**: 同一ノードの異なる向きのバケット（例: rightバケットとbottomバケット）は
それぞれ独立した`runElkLayout`呼び出しで配置されるため、互いの存在を一切考慮しない。実装後の目視確認
（レビュー時点のスクリーンショット参照）で、右側の子孫と下側の子孫が実際に視覚的に重なるケースを確認している。
ノード数が増えるほど発生しやすくなる、この設計に内在する制限。将来的に軽減するなら、各バケットのELK結果を
合成した後に「他バケットの外接矩形と重ならないよう外側へ押し出す」後処理パスを追加する方向が考えられるが、
現時点（検討中フェーズ）では未実装。

### 方針B: `flat-axis`（`src/utils/flatAxisLayout.ts`）

全エッジを横系・縦系に分け、マップ全体に対してELKを2回（横系のみRIGHT・縦系のみDOWN）実行し、
ノードごとの「支配軸」に応じてどちらの結果の座標を使うか決める。
手順の詳細は [align-algorithms.md](./align-algorithms.md) §3。

再帰・木構築が無いぶん方針Aよりずっと単純だが、x座標とy座標が別々の最適化結果からの寄せ集めになるため、
理論的な一貫性（重なり回避等）は保証されない。方針Aの複雑さが実際に見合うものかを判断するための比較対象。

### 方針E: `sugiyama-ext`（`src/utils/sugiyamaExtLayout.ts`）

ユーザー要望（右向きレイアウト前提）:「右ハンドルに繋いだ子は右方向の階層に、上/下ハンドルに繋いだ子は
親に少し被る形で上/下に配置したい」。これを、方針Aの再帰ボックス合成ではなく **スギヤマの4フェーズ
（[graph-drawing-primer.md §4-B](./graph-drawing-primer.md)）を拡張する形** で実装したもの。ELKは
1実行=1方向・整数レイヤーしか扱えず「半レイヤーぶんの重なり」を表現できないため、**ELKを使わず自前で
（同期処理として）実装**している。

手順の詳細（層割当のロンゲストパス、箱の再帰合成、`separateTrees` の押し離し）は
[align-algorithms.md](./align-algorithms.md) §4。`primary`/`cross` 軸とハンドル役割の対応表は同 §0.3。

**設計上の判断・デフォルト（ユーザー未指定の点。変えたい場合はここを見る）**:

- **backward（左/上）ハンドルの扱い**: ユーザー仕様は右・上・下のみ言及。left（RIGHT時）/top（DOWN時）は、要望に無かったエッジケースとして **forwardの鏡像**（-1層、親の後方へ、cross中央寄せ）をデフォルトにした。もし「後方ハンドルも上/下と同じ被せ配置がよい」等の意図があれば変更する。
- **被り量** `CROSS_OVERLAP_RATIO`: 0=全被り、親のprimary前半分に被る／1=被らない。目視で調整可能（`src/utils/sugiyamaExtLayout.ts` 冒頭、[tuning.md](./tuning.md)に記載）。
- **交差削減の効き**: 全域木＋非重なりボックス配置では、木エッジ同士は原理的に交差しない（交差はcross群の被りや非木エッジで生じる）。そのため「2層交差最小化」はforward群の子孫の絡まりを減らす程度の効果に留まる。要望どおりバリセンタ順を実装したが、木では並びが変わらないことも多い。
- **ツリー分離の押し離し**: `separateTrees` は「食い込みが小さい軸に沿って半分ずつ押し離す」反復（`TREE_SEPARATION_MAX_ITER` 回上限）。ツリー数が少ない前提で十分収束する。多数ツリーで密集した場合、上限到達で微小な残り重なりが出る可能性はある（実用上まれ）。

**改善履歴・残る制限**: 当初は「cross群とforward群のcross方向オーバーラップ」「複数ツリー間の重なり」「BFSによる浅いレイヤ採用」があったが、レイヤー割当〜座標割当の改良（ロンゲストパス／箱の外側積み／`separateTrees`。align-algorithms.md §4）で対処済み。ただし cross群のサブツリーが**さらに深い階層**で forward側の孫と近接する複雑ケースは、各ノード局所での分離のため完全には保証しない（検討中フェーズ）。

### 方針F: `elk-port`（`src/utils/elkPortLayout.ts`）

`uniform`（素のELK layered）は、ノードとエッジしかELKに渡していない（[layout.ts](../src/utils/layout.ts)の
`children` は `{id,width,height,x,y}`、`edges` は `{id,sources,targets}` のみ）。つまり `sourceHandle` は
**ELKに渡る前に捨てられている**。一方でELK layeredは**ポート制約をネイティブに持っている**
（[layout-prior-art.md](./layout-prior-art.md) P2。ELKのlayeredはポート制約付き階層レイアウトの論文実装そのもの）。
そこで「ハンドル情報をELKに渡すだけでどこまで良くなるのか」を測るために実装したのが方針F。

ノードごとに「実際に使われているハンドル面」ぶんのポートを作り、`elk.portConstraints: FIXED_SIDE` と
`elk.port.side` で面を固定してELKに渡す。それ以外のレイアウトオプションと位置ヒントの渡し方は `uniform` と
共有している（`layout.ts` の `ELK_BASE_LAYOUT_OPTIONS`）ので、差分安定性（[decisions.md §26](./decisions.md)）を
そのまま引き継ぎ、**`uniform` との違いはポートの有無だけ**という比較になる。
手順の詳細は [align-algorithms.md](./align-algorithms.md) §5。

**この方式の限界（重要。ポートは「取り付き面」であって「伸びる向き」ではない）**:
ポート制約は**単一の流れ方向（`elk.direction`）を保ったまま**エッジの取り付き面と面内順序を制御する仕組みで、
「上ハンドルの枝だけ流れ方向を上向きに変える」ことはできない。したがって RIGHT 方向では下ハンドルに繋いだ子も
右隣のレイヤーに置かれ、エッジだけが下面から出て回り込む。**方針Fは要望（右の子と下の子を分けて整列したい）
そのものは解かない**。ハンドルの向きどおりに子を配置するのは方針Eの役割で、方針Fは
「ELKネイティブ機能だけでどこまで行けるか」の上限を示す比較対象という位置づけ。契約（`CONTRACTS`）にも
`HANDLE_DIRECTION` は入れていない。

**測定結果（43ケース×`--scale`。詳細は [layout-lab.md](./layout-lab.md)）**:

- ハンドル向き不一致は `uniform` の 43 → **18** に減った。ポートは流れ方向を変えないが、レイヤ内の順序と
  ノード配置には効いており、「下ハンドルの子が下寄りに置かれる」程度の改善は起きる。ただし `sugiyama-ext` の
  **0** には遠く及ばない。
- 重なりは0（ELK任せなので `uniform` と同じく契約を満たす）。エッジ交差は 802 → 799 でほぼ変化なし。
- **エッジのノード貫通は 188 → 235 と悪化した**。理由は下記「ELKのエッジ配線はアプリに届いていない」。
- 実行時間・面積・移動量は `uniform` とほぼ同等（ポートを足したぶんのコストは誤差レベル）。

**ELKのエッジ配線はアプリに届いていない（方針Fの価値を大きく削ぐ構造的な事実）**:
ポート制約の主な利得は「ELKが取り付き面を踏まえてエッジを賢く配線する（曲げ点を計算する）」ことにある。
しかし `LayoutResult` は**ノード座標しか返しておらず**、アプリの描画は React Flow のベジェ曲線
（[CustomEdge.tsx](../src/components/Editor/CustomEdge.tsx)）で、ハンドルからハンドルへ直接引かれる。
ELKが計算した曲げ点は捨てられている。つまり**配線の改善は画面に一切現れず、ノード配置への間接的な影響しか
得られない**。貫通が悪化したのはこのため（ELKは「回り込む配線」を前提に配置を決めるが、アプリはそこを直線的な
ベジェで結ぶ）。方針Fを本気で活かすなら、`LayoutResult` にエッジの曲げ点を持たせて React Flow 側を
折れ線エッジに変える、という**描画側の変更とセット**になる。これは整列アルゴリズムの選択とは別の意思決定。

**設計上の判断（ユーザー未指定の点。変えたい場合はここを見る）**:

- **ポートは「面ごとに1つ」でエッジ間で共有する**（エッジごとに別ポートを作らない）。React Flowのハンドルが
  各辺に1つしかなく、同じ面から出る全エッジが同じ点から描かれるため、そちらに合わせた。エッジごとに
  ポートを分けると、ELKは実際には存在しない「面内の複数の取り付き点」を前提に配置してしまう。
- **`FIXED_SIDE` を採用し `FIXED_POS`（座標まで固定）は不採用**。面ごとに1ポートしか無い場合、ELKはその
  ポートを辺の中点に置くため、辺の中点座標を明示する `FIXED_POS` と**結果が完全に一致する**ことを実測で確認した。
  同じ結果ならノード幅・高さからポート座標を自前計算する `FIXED_POS` は無駄に壊れやすいので採らない。
- **ポートサイズは0**（`PORT_SIZE`、[tuning.md](./tuning.md)）。正の値にするとポートがノードの外側に張り出し、
  そのぶんレイヤー間隔が広がる。0ならポート位置が辺上の1点になり、React Flowのハンドル位置および評価環境の
  アンカー計算（`e2e/lib/layout-metrics.mjs` の `anchorOf`）と一致する。
- **`elk.port.side` は描画上の実際の面に1対1で対応させる**（`elk.direction` に応じて回転させたりしない）。
  ELK側が方向に応じた内部的な回転を吸収するため、DOWN方向でもそのまま正しく動く。この対応を取り違えると
  （例: top↔bottom を入れ替える）コーパス全体のハンドル向き不一致が 18 → 56 に跳ね上がるので、
  ベースライン回帰テストが検知する。

### 方針G: `elk-port-ext`（`src/utils/elkPortExtLayout.ts`）

方針Fは「elkjsにポートを渡すだけ」なので、中身を触って改善することができない（ELKのオプションで
表現できることしかできない）。**方針Fと同じ枠組みを、ELKに依存せず必要最小限だけ自前で書き直したもの**が
方針G。ELKの実装を移植したのではなく、スギヤマの枠組み＋ポート制約という考え方を最小構成で実装している。
`sugiyama-ext`（方針E）が「ハンドルの向きで層を変える」独自路線なのに対し、方針Gは
**ELKと同じ土俵（単一の流れ方向）に留まったまま**、各フェーズを差し替え可能にした版。

**5フェーズ**は 循環除去 → レイヤー割当 → 仮想ノード（長いエッジの分解）→ 交差削減 → 座標割当。
ELK layered と同じ構成だが、**座標割当だけ Brandes–Köpf ではなく「層内の順序と最小間隔を守った上で
希望位置との重み付き二乗誤差を最小化する」問題を PAVA（等調回帰）で厳密に解く**形にしてある。
各フェーズの具体的な処理・データ構造・式は [align-algorithms.md](./align-algorithms.md) §6。

**ポート制約がどこに効くか**: 「エッジの端点はノードの中心ではなくハンドル（ポート）の位置である」という
一点を、4・5フェーズのバリセンタ計算に入れるだけ。流れ方向の面（RIGHT時のright/left）に付いたポートは
cross方向のオフセット0、直交方向の面（RIGHT時のtop/bottom）に付いたポートはノードのcross方向の端＋
`PORT_STUB` だけずれる。結果として下ハンドルの子は親の下へ、上ハンドルの子は親の上へ引っぱられる。
**ELKが北/南ポートのために同じ層へダミーノードを挿入して確保する空間を、ダミーを実体化せずに
オフセットで表現したもの**、という関係になっている。

なお方針Fと同じく、**流れ方向そのものは単一のまま**（下ハンドルの子も前方の層に置かれる）。

**測定結果（43ケース×`--scale`。詳細は [layout-lab.md](./layout-lab.md)）**: 方針Fを全面的に上回った。

| 指標 | `elk-port`(F) | `elk-port-ext`(G) | `sugiyama-ext`(E) |
|---|---|---|---|
| 重なりノード対 | 0 | **0** | 0 |
| ハンドル向き不一致 | 18 | **17** | 0 |
| エッジ交差 | 799 | **209** | 2 |
| エッジのノード貫通 | 235 | **52** | 46 |
| 描画面積(千px²) | 30351 | **24719** | 24813 |
| 平均移動量 | 369 | **185** | 164 |
| 兄弟順の反転率 | 0.006 | **0.045** | 0.013 |
| 実行時間(ms) | 851 | **51** | 24 |

交差 799→209・貫通 235→52 の改善は主に**仮想ノード（フェーズ3）**の寄与。ELK本体も同じことを
しているが、ELKは「回り込むエッジ配線」を前提に配置するのに対し、こちらは配線を作らない前提で
配置するため、**アプリの描画（ハンドル間の直線的なベジェ）と噛み合う**。方針Fの貫通が悪化した
理由の裏返しになっている。移動量が小さいのは、原点付近へ正規化せず**入力の外接矩形の左上に
合わせて平行移動する**ため（ELK本体にはこの選択肢が無い）。

**唯一の弱点は兄弟順の反転率（0.045で全方式中いちばん悪い）**。交差削減（フェーズ4）が
「交差が減るなら並べ替える」ため。`ORDERING_SWEEPS` を 0 にすると交差削減が丸ごと止まり、
このトレードオフがはっきり出る:

| `ORDERING_SWEEPS` | 交差 | 貫通 | 向き不一致 | 面積(千px²) | 兄弟順の反転率 |
|---|---|---|---|---|---|
| 4（現在） | 209 | 52 | 17 | 24719 | 0.045 |
| 0（交差削減なし） | 801 | 229 | 10 | 22956 | 0.006 |

交差・貫通の改善幅のほうが大きいので既定は 4。**「兄弟順を保つ」を重く見るなら、交差削減を
止めるのではなく「一定以上改善するときだけ並べ替える」しきい値を入れるのが次の一手**（未実装）。

**改善の入口（このファイルのどこを触ると何が変わるか）**:

- **フェーズ5を Brandes–Köpf に差し替える**: 現在のPAVA掃引は各層を局所的に解くだけなので、
  層をまたいだ「まっすぐさ」はダミーの重み（`DUMMY_WEIGHT`）で間接的にしか効いていない。
  BKの4方向アライメント＋平均化に置き換えると、長い枝の直線性が上がる可能性がある。
- **フェーズ4に交差削減のしきい値を入れる**: 上記の兄弟順トレードオフ対策。
- **ポートの扱いを強める**: `PORT_STUB` を大きくすると上/下ハンドルの子が親から強く離れる。
  さらに進めて「直交ポートの子は層を進めない（＝方針Eの0.5層）」まで行くと `sugiyama-ext` に近づく。
  **方針Eと方針Gの中間を探れるのがこの実装を持つ意味**。
- **エッジの曲げ点を返す**: フェーズ3の仮想ノードは、そのまま折れ線エッジの曲げ点になる。
  `LayoutResult` を拡張して React Flow 側を折れ線に変えれば、方針Fの節で書いた
  「ELKの配線がアプリに届かない」問題を自前で解決できる。

**設計上の判断（ユーザー未指定の点）**:

- **座標割当にBrandes–Köpfを使わなかった**: BKは4方向のアライメント＋平衡化で実装量が大きく、
  「必要最小限の再実装」という趣旨から外れる。PAVA版は「順序と間隔の制約下で希望位置に最も近い配置」を
  **厳密に**解くので、局所解の心配がなく、掃引回数以外に調整すべき隠れパラメータが無い。
- **原点正規化ではなく元位置へのアンカー**: ELK本体は結果を原点付近へ正規化するためマップ全体が飛ぶ。
  自前実装ではその必要が無いので、整列後の外接矩形の左上を入力の左上に合わせる
  （`sugiyama-ext` がrootの現在位置を保つのと同じ思想。[decisions.md §26](./decisions.md)）。
- **ポート役割（`PortRole`）を `sugiyamaExtLayout.ts` と共有していない**: 同名の概念だが、あちらは
  「役割で層を変える」ため、こちらは「役割でcross方向の取り付き位置を変える」ために使う。用途が違い、
  片方を削除するときに巻き込まれないよう独立に持たせている。

## 切り替え方法（本番=sugiyama-ext・比較切り替えはdev限定）

**本番ビルドの既定アルゴリズムは `sugiyama-ext`（暫定採用）**。`src/hooks/useAlignAlgorithmDebug.ts` の
`DEFAULT_ALGORITHM` に一元化してあり、本番では常にこの値を返す（dev環境で保存値が無いときのフォールバックでもあるので、
devで確認する挙動が本番と一致する）。ユーザー向けUIと開発用機能を混ぜない方針（プロジェクト共通ルール）に従い、
`uniform`/`branch`/`flat-axis`/`sugiyama-ext`/`elk-port`/`elk-port-ext` を**比較して切り替えるUIはdev限定**とし、`import.meta.env.DEV` が真のとき
（`npm run dev` 実行時）のみツールバーに現れる選択欄から切り替えられる。選択内容は `localStorage`
（キー `mindmeshmap-debug-align-algorithm`）に保存され、dev環境でのリロード間で維持される。本番ビルドではこの
localStorageキーを読まない（dev判定はコード側にもハードコードしてあり、UIの出し分けだけに頼らない）。
既定を他アルゴリズムに戻す/変えるときは `DEFAULT_ALGORITHM` を書き換える。

**実装上の罠（既に踏んで修正済み）**: 切り替え状態は `useAlignAlgorithmDebug`（`src/hooks/`）で持つが、
これは**Zustandストア**で共有している。書き込み側（Toolbarのセレクト）と読み取り側（`useAutoLayout.applyLayout`）は
別コンポーネント/フックなので、コンポーネントローカルの `useState` にすると各自が独立した状態を持ち、セレクトを
変えても整列側に伝わらず「切り替えても常に既定アルゴリズムで実行される」不具合になる。実際に一度この作りで実装して
発生させた。共有ストアにして変更が即座に読み取り側へ伝わるようにすること（詳細はフック冒頭のコメント参照）。

具体的な実装箇所は [tuning.md](./tuning.md) に一覧化する（実装後に追記）。

## 今後の運び

現在は `sugiyama-ext` を本番の既定に暫定採用しているが、比較切り替えUIと他候補のコードはまだ残してある。
しばらく `branch` / `flat-axis` / `sugiyama-ext` / `elk-port` / `elk-port-ext`（および `uniform`）を実際に触って比較し、最終的にどれかに確定したら:

1. 決定内容と理由を [decisions.md](./decisions.md) に新しい決定記録として追加する（このメモの内容を要約・整理して移す）。
2. 採用しなかった候補のファイル（`branchLayout.ts` / `flatAxisLayout.ts` / `sugiyamaExtLayout.ts` /
   `elkPortLayout.ts` / `elkPortExtLayout.ts` のうち不採用のもの）とdev切り替えUI・関連テストを削除する（不要になったファイルは残さない、というプロジェクト共通方針）。
   なお `branchLayout.ts` は `classifyEdgeSide` / `HandleSide` を `sugiyamaExtLayout.ts`・`elkPortLayout.ts`・
   評価環境（`e2e/lib/layout-metrics.mjs`）へ提供しているので、`branch` を落とす場合はこの2つの移設が要る。
3. このメモ（`align-branch-layout.md`）は決定記録への移行が終わったら削除するか、検討過程の記録として
   decisions.mdからリンクする形で残すかを、その時点で判断する。
