# 設計決定記録

MindMeshMap における設計判断のうち、選択肢を比較して決めたものを記録する。
「同じ議論を二度しない・同じ轍を踏まない」ための永続化が目的。採用理由だけでなく、不採用案とその理由（＝逆戻りガード）・再検討の条件も残す。

---

## 1. ローカル下書きは localStorage への常時保存

- **決定**: `currentMap` の変更を 500ms デバウンスで `localStorage`（キー `mindmeshmap-draft`）に常時保存し、起動時に復元する。未ログインでもマップが消えないようにするための仕組み。
- **採用理由**:
  - 実装が単純（同期API、追加依存なし）で、個人プロジェクトのランニングコストゼロ方針に合致する。
  - 採用実例: Excalidraw はシーン（要素・アプリ状態）をブラウザの永続化ストレージに常時保存し、リロード後も編集内容を復元する設計を採っている。同様のパターンは多くのオフラインファーストなブラウザエディタで採用されている。
- **不採用案とその理由**:
  - **IndexedDB**: 非同期APIでスキーマ設計や容量管理の実装コストがかかる。マインドマップ1件分のJSONサイズ（数十〜数百KB程度）に対しては過剰。
  - **beforeunload 警告のみで永続化はしない**: タブクラッシュ・ブラウザクラッシュ・誤ってタブを閉じた場合に変更が失われる。警告はユーザー操作を前提とするため根本的な対策にならない。
- **制限**: 複数タブで同時に編集した場合は最後に書き込んだタブが勝つ（後勝ち）。タブ間の同期・マージは行わない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 1マップあたりのデータ量が大きくなり localStorage の容量上限（ブラウザ依存、目安5MB程度）に近づく場合、または複数タブ編集のユースケースが増える場合に IndexedDB への移行を再検討する。

## 2. Drive オートセーブは保存済みマップのみ対象

- **決定**: Google Drive への自動保存（3秒デバウンス）は、既に Drive に保存済みのマップ（`currentFileId` がある）のみを対象とする。新規マップは対象外。
- **採用理由**: 初回保存を明示操作（保存ボタン / Ctrl+S）に限定することで、ユーザーが意図しないタイミングで Drive 上にファイルが作られることを防ぐ。
- **不採用案とその理由**:
  - **新規マップも自動保存の対象にする**: ちょっと開いて何も保存する気がないマップでも "New Map" のようなファイルが Drive 上に乱造される。ユーザーの Drive を汚し、マップ一覧のノイズになる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（現状の方針を維持）。

## 3. 認証トークンは sessionStorage + expiresAt 管理

- **決定**: Google Identity Services (GIS) の implicit flow で取得したアクセストークンとその有効期限（`expiresAt`）を `sessionStorage` に保存し、タブ単位で永続化する。有効期限切れを検知したら「再ログイン」ボタン付きトーストを表示する。
- **採用理由**:
  - `sessionStorage` はタブを閉じると自動的にクリアされるため、`localStorage` より露出面が狭い。
  - バックエンドを持たない静的ホスティング構成（個人プロジェクトのランニングコストゼロ方針）でも実装できる。
- **不採用案とその理由**:
  - **localStorage に保存**: XSS 発生時の露出面が広く、タブを跨いで（ブラウザを閉じても）トークンが残り続ける。
  - **メモリのみ保持（どこにも永続化しない）**: リロードのたびに再ログインが必要になり、UXが著しく悪化する。
  - **リフレッシュトークンを併用する**: GIS の implicit flow ではリフレッシュトークンは取得できない（authorization code flow が必要）。authorization code flow はトークン交換にクライアントシークレットを扱うバックエンドが必須になり、「個人プロジェクトはランニングコストゼロ」の方針に反する。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: バックエンドを持つ構成に移行する場合（例: 有料プランや複数ユーザー向け機能を追加する場合）は authorization code flow + リフレッシュトークンを再検討する。

## 4. 通知は自作トースト（右下）+ 独自確認ダイアログ

- **決定**: `alert` / `confirm` を廃止し、`toastStore` によるトースト通知（右下、アクションボタン対応）と `confirmStore` による独自確認ダイアログ（`window.confirm` の Promise版代替）に統一する。
- **採用理由**: `alert`/`confirm` はブラウザ標準のモーダルで見た目のカスタマイズができず、アプリのUIトーンと合わない。また同期的にスクリプト実行をブロックするため、UXが硬い。
- **不採用案とその理由**:
  - **react-hot-toast 等の外部ライブラリ**: 要件（成功/エラー/情報の3種、アクションボタン、自動消去）が単純でZustandストア + 数十行のコンポーネントで十分自作できる。外部依存を増やさない方針を優先した。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 通知の種類（スタック順、アニメーション、位置指定など）が複雑化し自作コストが上回る場合。

## 5. PNG エクスポートは html-to-image

- **決定**: マインドマップの PNG エクスポートに `html-to-image` の `toPng` を使う。
- **採用理由**: React Flow 公式の [download-image サンプル](https://reactflow.dev/examples/misc/download-image) が採用しているライブラリであり、React Flow のノード・エッジDOMをそのまま画像化する用途に対して実績・親和性がある。

## 6. 書式GUIはキャンバス右上の常設パネル + Tiptap BubbleMenu の併存

- **決定**: リッチテキストの書式操作（太字・斜体・打ち消し線・箇条書き・番号リスト）は、(1) ノード編集中はキャンバス右上に常設表示される書式パネル（`FormatToolbar`）と、(2) テキスト選択時にだけ選択範囲のそばに表示される Tiptap の `BubbleMenu` の両方で提供する。両者は操作対象・操作内容が同じで、表示位置とトリガー条件が異なるだけ。
- **経緯**: 当初は BubbleMenu のみを採用していたが（旧決定）、「テキストを選択しないと書式操作の入口が見えない＝発見性が低い」という課題が残った。ノードごとに常設ツールバーを置く案は多数ノードが並ぶキャンバスを視覚的に煩雑にするため不採用のままとし、代わりに「編集中のノードは常に1つ（またはゼロ）」という性質を利用し、キャンバス側（ノード側ではない）に1箇所だけ常設パネルを置く方式にした。
- **採用理由**:
  - キャンバス右上の固定位置なら、ノード数が増えてもパネルは常に1個で済み、キャンバスが煩雑にならない。
  - BubbleMenu はテキストの一部だけを選択して書式を当てたい場合（部分書式）に引き続き有用なため、置き換えずに併存させた。
- **不採用案とその理由**:
  - **ノードごとの常設ツールバー**: 上記の通り、ノード数分のツールバーが同一画面に並び視覚的に重い（決定当初からの不採用理由を維持）。
  - **BubbleMenuを常設パネルに完全に置き換える**: 部分選択への書式適用（例: 文中の一部だけ太字にする）のトリガーとしてテキスト選択は自然な操作であり、失うとUXが後退する。
- **実装上の注意**: 常設パネル（`FormatToolbar`）は編集中のTiptapエディタインスタンスを `editorStore`（`activeEditor`）経由で参照する。ノードごとの `BubbleMenu` を `isEditing` に応じて安全に有効/無効化する方法については決定17を参照。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（両方式併存を現行方針として維持）。

## 7. モバイルは「1タップ選択 → 再タップ編集」

- **決定**: モバイルでのノード操作は、未選択ノードへの1回目のタップは選択のみ、選択済みノードへの2回目のタップで編集モードに入る2段階方式にする。
- **採用理由**: XMind・MindMeister など主要なモバイル向けマインドマップアプリが採用している標準的なパターン。選択だけしたい操作（ドラッグ前の選択、複数選択の起点など）でソフトウェアキーボードが毎回開くのを防げる。
- **不採用案とその理由**:
  - **タップ即編集**: ノードを見るためだけ・移動させるためだけにタップしてもキーボードが開いてしまい、意図しない編集モード突入が頻発する。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。

## 8. Undo はテキスト編集1セッション=1ステップ、ドラッグは開始時スナップショット

- **決定**:
  - テキスト編集: 編集セッション中の最初の変更のみ履歴（history）に積み、以降の同一セッション内の変更は履歴を積まない。これにより「1文字ずつUndoが戻る」のではなく「編集開始前の状態に1回のUndoで戻る」体験になる。
  - ノードドラッグ: `onNodeDragStart` の時点でドラッグ前のスナップショットを履歴に積み、ドラッグ中・ドラッグ終了時は位置のみを更新して履歴を積まない。これによりドラッグ全体が1 Undoステップになる。
- **採用理由**: 文字単位・座標更新単位でUndo履歴を積むと、Undoを何度も押さないと意図した単位まで戻らずUXが悪い。「意味のある操作の単位」でUndoが機能する方が直感的。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（現状の方針を維持）。

## 9. リネームのDrive反映は uploadType=multipart の PATCH 1回

- **決定**: マップのタイトルをリネームして保存すると、Google Drive 上のファイル名とファイル内容（マップJSON）を `uploadType=multipart` の PATCH リクエスト1回で同時更新する。
- **採用理由**: 名前とコンテンツを同一リクエストで更新できるため、途中失敗時に「名前だけ変わって内容が古いまま」のような不整合が起きない。
- **不採用案とその理由**:
  - **メタデータPATCH（名前変更）とコンテンツ更新を別リクエストにする**: 2リクエストの間にエラーが起きると部分的にしか更新されない状態（名前は変わったが内容は古い、またはその逆）が発生しうる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。

## 10. OGP の og:image を専用バナー画像で設定（英語をデフォルト・日本語版も同梱）

- **決定**: 1200×630px の専用バナー画像を用意し、`index.html` に `og:image`（絶対URL）・`og:image:width/height`・`og:image:alt`・`og:locale`（`en_US`）・`twitter:image` を追加。`twitter:card` は `summary` から `summary_large_image` に変更した。**デフォルト（共有時に必ず出る画像）は英語版 `public/og-image.png`**。日本語版 `public/og-image.ja.png` も同梱する。
- **英語をデフォルトにした理由**: サイトのメタは元々英語基調（`<html lang="en">`、`fallbackLng: 'en'`、`og:title`/`og:description` が英語）。共有時に必ず表示される1枚を英語に揃えることで、より広いオーディエンスに届く。
- **なぜロケール自動切替にしないか（重要・逆戻りガード）**: OGP画像は「1URL＝1枚」で静的に固定され、**閲覧者の言語に応じてSNS/Slack側が自動で出し分けることはできない**。クローラはJSを実行しないため、アプリ内の言語切替（i18next）やJSでの`<meta>`書き換えは共有プレビューに反映されない。また GitHub Pages は静的ホスティングでロケール別HTMLの出し分け（サーバサイドのコンテンツネゴシエーション）ができないため、`og:locale:alternate` によるFacebookのロケールURL切替も機能しない。したがって「デフォルト＝英語」を固定し、日本語版はファイルとして同梱（`.../og-image.ja.png`）するに留める。ロケール別に確実に出し分けたい場合は、ロケール別の静的HTML（別URL）を用意して各々の `og:image` を差し替える必要がある（現時点では過剰と判断し不採用）。
- **画像の内容**: アプリのブランド（ダークテーマ・ブルーのアクセント `#5b9fe6`/`#63b3ed`、`public/logo.svg` のメッシュモチーフ）に合わせ、左にタイトル「Mind Mesh Map」＋タグライン＋機能チップ＋公開URL、右に**循環を含むノードグラフ**（4ノードのループを明色で強調＋横断リンク）を配置。本アプリ最大の特徴である「循環許容」を一目で伝えることを狙った。実アプリのスクリーンショットではなく、縮小表示でも要点が読める専用バナーを採用。ロケール別の差分は文言のみ（英: A graph-structured mind map editor that allows cycles / 日: 循環を許容するグラフ構造のマインドマップエディタ、機能チップ、グラフのノードラベル）。
- **生成方法**: `scripts/og-image.gen.mjs`（devDependency の Playwright + Chromium で HTML をスクリーンショット）。リポジトリルートで `node scripts/og-image.gen.mjs` を実行すると **`public/og-image.png`（en）と `public/og-image.ja.png`（ja）を両方再生成**する。文言調整はスクリプト冒頭の `LOCALES`、グラフの見た目は `geometry`/`edges` を編集する。生成物のみ配布（`public/`）、生成スクリプトは `scripts/` 配下に置きビルド成果物へは混入させない。

## 11. PNGエクスポートのbounds算出はDOM実測（offsetWidth/offsetHeight）

- **決定**: PNGエクスポート時のマップ全体のbounds（左上・右下座標）は、React Flowの `getNodesBounds()`（`node.measured` 依存）を使わず、`getNodes()` のposition（ドラッグ中の最新値を含む）と、各ノードのDOM要素（`.react-flow__node[data-id="..."]`）の `offsetWidth` / `offsetHeight`（transformの影響を受けないレイアウト実寸）から自前で組み立てる。
- **背景**: 本アプリは `onNodesChange` の `dimensions` 変更（React Flowが `ResizeObserver` で計測したノードサイズ）を独自の状態に反映していないため、`node.measured` が常に空になる。そのため `getNodesBounds()` はノードをサイズ0の点として扱ってしまい、右端・下端のノードが画像から見切れる不具合があった。
- **採用理由**: `offsetWidth`/`offsetHeight` はDOM実測値のため、`measured` を経由せず正確なノードサイズが得られる。既存のノード管理フロー（`currentMap.nodes` → React Flow の `nodes` props）を変更する必要がない。
- **不採用案とその理由**:
  - **React Flowの `measured` をストアに同期する**: `onNodesChange` の `dimensions` 変更を `mapStore` に反映する経路を新設する必要があり、キャンバス状態フロー（ノード変更 → ストア → 再描画）への影響範囲が広い。PNGエクスポートという限定的な用途のためだけに、常時発火する `dimensions` 変更のハンドリングを追加するのは割に合わない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 将来的に `measured` を他の用途（例: 自動レイアウトでの実サイズ考慮）でも使うようになり、ストアに同期する経路がどのみち必要になった場合は、この自前計算をやめて `measured` ベースに統一することを検討する。

## 12. React Flowの `zoomOnDoubleClick` は無効化する

  - **ダブルクリックズームを維持し、ノード作成は別操作に割り当てる**: 「空白をダブルクリックしてノードを作る」という直感的な操作を手放すことになり、UXの後退が大きい。

## 13. IME対応は「armed-focus」方式（3回目の反復で確立。前2方式は失敗）

- **決定**: 選択中（かつ編集中でない）ノードのTiptapエディタを常時 `editable: true` にして事前にDOMフォーカスを当てておく（キャレットはCSSで透明化し、見た目上は編集中に見えないようにする）。この状態を「armed」と呼ぶ。armed中に印字可能文字が打鍵されたら、その打鍵イベント自体はTiptap/ブラウザのデフォルト処理（IME処理を含む）にそのまま委ねつつ（`editorProps.handleKeyDown` で `return false`）、アプリ側は同じコミット内で `flushSync` により編集モードへ遷移させる。矢印キー・Tab・Enter・Ctrl系等の非印字キーはProseMirrorに処理させず（`return true`）windowまでバブルさせ、`useKeyboardShortcuts` 側でノード操作として扱う。

- **改訂（3回目の反復では不十分だった点。4回目で完成）**: armed-focus方式を最初に入れた時点では、以下2つの見落としにより「マウスでノードを作ってそのまま入力すると1文字目が英数字になる」不具合が残っていた。CDPで各作成経路の `document.activeElement` を観測して真因を特定し、次の2点で解決した。
  1. **マウス作成（ダブルクリック / ハンドルドラッグ）は armed を経由せず即編集モード（`setEditingNodeId`）に入るため、armed-focusの「打鍵前フォーカス」保証の対象外だった。** かつ編集モードの `useLayoutEffect` にはフォーカスのrafリトライが無く、armedブロックにしか無かった。そのため、React Flowが新規ノードを寸法計測完了まで `visibility:hidden` で描画する間にフォーカスが確立できず、作成直後は `document.activeElement` が `body` のまま最初の打鍵が来ていた（＝IMEがフォーカス要素を定められず1文字目を生ASCIIで確定）。→ **編集モードのフォーカス確立にもarmedと同じrafリトライを共通化して追加**（`focusWithRetry`）。これが本丸の修正。
  2. **編集モード遷移時に既存内容を消す `clearContent`（`pendingEditClear`）が、compositionと同じタイミングで走るとProseMirrorのドキュメント差し替えでcompositionを壊す潜在リスクがあった。** → **新規作成ノードを空にして（`utils/nodeContent.ts` の `EMPTY_NODE_CONTENT`、Placeholderで案内）、`clearContent`/`pendingEditClear` を完全に廃止した。** これに伴い「armedからタイプ開始で既存内容を置換」という旧仕様は「末尾に追記」へ変更（新規ノードは空なので実質は純粋入力。既存の内容があるノードを選択していきなりタイプした場合のみ追記になる。非破壊で安全側）。置換を維持するには打鍵前に `selectAll` しておく手があるが、`selectAll` + IME + ProseMirror の相互作用が実機依存で不確実なため、「1文字目を確実に直す」ことを優先し、compositionと競合しうる内容操作（`clearContent`/`selectAll`）は一切持ち込まない方針にした。
- **経緯（同じ轍を踏まないための記録）**: この挙動に至るまでに3回実装を反復しており、**最初の2回はどちらも実際のIME環境で1文字目の変換に失敗した**。
  1. **第1版: pendingEditChar方式**（最初の1文字をアプリ側で保持し、編集モード開始後に `insertContent` で挿入）。IME変換を経ない生のASCII文字がそのまま挿入されてしまい、ローマ字→かな変換前の文字が確定した状態になる。日本語IME利用時は実用にならず不採用。
  2. **第2版: keydownハンドラ内でのflushSync同期フォーカス方式**（`useKeyboardShortcuts` の `keydown` ハンドラ内で `flushSync` を使い「ノード選択→編集モードへ」の状態更新を同期的にフラッシュし、`CustomNode` 側の `useLayoutEffect` で `editor.view.dom.focus()` も同じコミット内で同期的に行う。文字の横取りはしない）。DOMフォーカス自体は同期的に確定するため一見動きそうに見えるが、**ブラウザ（IME）は「その keydown イベントが発生した時点で既にフォーカスされていた要素」を基準にcomposition開始を判断するため、同じ keydown イベントのハンドラ内でどれだけ同期的にフォーカスを移しても、その1回の打鍵自体には間に合わない**。次の打鍵からは正しく動くため一見「ほぼ動いている」ように見えてしまう点が罠で、1文字目だけ変換が効かない不具合として現れた。
  3. **第3版: armed-focus方式（採用）**。打鍵の「前」からフォーカスがcontenteditableに存在することを保証することで、IMEが最初の打鍵から正しくcomposition開始を判断できるようにした。
- **注意喚起（このドキュメントの目的そのもの）**: **keydown時点でのフォーカス移動や、入力文字をアプリ側で保持して後から挿入する方式では、IMEの1文字目問題は解決できない。** IMEは「打鍵イベント発生時点で既にフォーカスされている要素」を見てcomposition開始を判断するため、対策は必ず「打鍵より前にフォーカスを確立しておく」形（armed-focus）でなければならない。今後IME関連の不具合に対処する際、上記2方式（またはその類型）を再度試みないこと。**加えて、フォーカスを確立する経路は armed だけでなく「マウス作成→即編集」も含む全経路で確実にすること（visibility:hidden のrafリトライを両方に入れる）。1文字目問題が『再発した』と感じたら、まず該当の作成経路で作成直後の `document.activeElement` が `.ProseMirror` になっているかをCDPで観測すること（`e2e/ime-input.mjs` がこの観測を自動化している）。`body` に抜けていればフォーカス確立の欠落が原因。**
- **採用理由**:
  - 打鍵前からフォーカスが正しい要素にあるため、日本語IMEでも1文字目から変換候補が正しく効く。
  - 文字を横取りしない（ネイティブ入力に任せる）ため、IME変換前の生文字が誤って入る余地がない。
- **実装上の落とし穴（armed-focusを今後触る際に再度踏まないための記録）**:
  - **Tiptapの `editor.commands.focus()`/`blur()` は内部で `requestAnimationFrame` 経由の非同期実行になる**（Tiptap側のコメントいわく "For React we have to focus asynchronously"）。armed化・編集モード遷移・他ノードへのフォーカス移動のように、同一コミット内で同期的にDOMフォーカスを確定させる必要がある場面では、これらのコマンドではなく `editor.view.dom.focus()` / `editor.view.dom.blur()` を直接呼ぶ必要がある。非同期のままだと、後から遅延実行されたblur()が、別ノードへの同期focus()の後に発火してフォーカスを奪ってしまう等の競合が起きる。
  - **新規ノード作成直後のフォーカス確立には、2種類の妨害要因がある。両方を1つの監視ループ（`focusWithRetry`）でカバーする。**
    1. **React Flowは新規追加ノードを、寸法計測が完了するまで `visibility:hidden` で描画する**（計測完了後にvisibleへ切り替える）。非表示要素はフォーカスできないため、作成直後の同期 `focus()` が失敗する（可視化後に取り戻す必要がある）。
    2. **ハンドルからエッジを引き伸ばして作る経路（`onConnectEnd`）では、d3-dragのpointerup後の後始末が非同期でフォーカスをキャンバス側へ奪う。** 一度 `focus()` が成功しても直後に奪われるため、「成功したら監視終了」では最初の打鍵時にフォーカスが抜けている（＝ハンドルドラッグ作成ノードで1文字目が英数字になる）。
    - 対策: `requestAnimationFrame` で `FOCUS_GUARD_FRAMES`（≒20フレーム）の間、毎フレーム「domにフォーカスが無ければ当て直す」監視を続ける（`src/components/Editor/CustomNode.tsx` の `focusWithRetry`、値は[tuning.md](./tuning.md)参照）。既にフォーカスがある間は `focus()` を呼ばない（no-op）ので正常操作を妨げない。別ノード選択等でeffectが再実行されればcleanupで監視は止まる。**このリトライは armed ブロックと編集モードブロックの両方に適用すること**（片方だけだと、その経路のノード作成でIME1文字目問題が残る）。
    - **重要な限界**: 上記(2)のd3-dragによるフォーカス奪取は、CDP経由のPlaywright（`page.mouse`のドラッグ）では再現できず、旧「一度成功で停止」方式でもCDP上はフォーカスが当たって見えた。つまりこの経路の不具合はCDPでは自動実証できず、**実機での確認が必須**（第2版のIME問題と同じ「実機のみで再現」の構造）。`e2e/ime-input.mjs` の経路Cは「作成ノードにフォーカスが当たりIME入力が入ること」までは自動で守るが、実機のフォーカス奪取タイミングそのものは検証できていない。
  - **ハンドルドラッグ経路（`onConnectEnd`）には、フォーカス確立より前段の「作った新ノードの選択・編集状態そのものが解除される」問題がある（こちらがユーザー報告『どこにもフォーカスされない／カーソルが出ない』の主因）。** ハンドルから引き伸ばして空白にドロップした時の pointerup が、pane の click として `onPaneClick` を誘発し、`setSelectedNodeId(null)`/`setEditingNodeId(null)` が走って、作ったばかりのノードがどこにも選択・編集されていない状態に戻ってしまう（当然フォーカスもIME入力も無い）。対策: `onConnectEnd` で新ノードを作った直後に `justConnectedRef` を立て、直後（300ms以内）の `onPaneClick` を1回だけ無視する（`src/components/Editor/MindMapCanvas.tsx`）。**この onPaneClick 誘発も CDP の `page.mouse` ドラッグでは自動では起きない**（CDPでは pane に DOM の `click` は飛ぶが React Flow の合成 `onPaneClick` には繋がらない＝状態が維持されて見える）。そのため `e2e/ime-input.mjs` の経路Cでは「ドラッグ後に明示的に pane をクリックして `onPaneClick` を発火させ、ガードが選択・編集を守ること」を検証している（`observe-guard` の観測では、ドラッグ直後300ms以内の pane クリックでは編集状態が維持され、300ms経過後の pane クリックでは通常どおり解除された＝ガードが正常動作を壊していないことも確認済み）。実機で本当に誘発されているかの最終確認は手動。
- **不採用案とその理由**: 上記「経緯」に記載の第1版・第2版を参照。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（現状の方式を維持）。

## 14. ノード内テキスト編集をUndo/Redo対応にする（外部content変更をエディタへ同期）

- **決定**: `mapStore` の history（Undo/Redo）でノードの `content` が巻き戻された際、`CustomNode` 側で「自分が編集中でない場合に限り」`data.content` の変化を検知して `editor.commands.setContent(parsed, false)`（`emitUpdate=false`）でTiptapエディタに反映する `useEffect` を追加した。

- **採用理由**: `emitUpdate=false` を指定することで、プログラム的な内容同期が `onUpdate`（延いては `saveToHistory`）を再発火させず、Undo操作自体が新たな履歴を積んでしまう無限ループを避けられる。「編集中でない場合のみ」に限定することで、自分自身の入力中に自分の内容で上書きされる競合も起きない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。

## 15. マップ一覧の並び順はクライアント側ソート + localStorage永続化

- **決定**: サイドバーのマップ一覧の並び順（更新日時/作成日時 × 新旧）は、Google Drive APIのクエリ（`orderBy`）を変更するのではなく、取得済みの一覧をクライアント側で毎回ソートし直す方式にする。選択した並び順は `localStorage`（キー `mindmeshmap-maplist-sort`）に保存し、次回訪問時も復元する。
- **採用理由**:
  - 一覧の件数は個人利用規模（数十件程度）を想定しており、クライアント側ソートのコストは無視できる。
  - Drive APIへの再フェッチなしに並び替えができ、切り替えが即座で操作感が良い。
  - `orderBy` パラメータを動的に切り替える実装（`useGoogleDrive.listMaps` の呼び出し元全てに並び順を伝搬する必要がある）よりも実装が単純。
- **不採用案とその理由**:
  - **Drive APIの `orderBy` を並び順に応じて切り替える**: 並び替えのたびに再フェッチが必要になりネットワーク待ちが発生する。一覧取得ロジック（`listMaps`）に並び順の引数を通す変更が必要になり、影響範囲が広がる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: マップ件数が非常に多くなり（数百件超)クライアント側ソートのコストが無視できなくなった場合に再検討する。

## 16. React Flowへ渡す nodes/edges 配列はidキーでオブジェクト参照をキャッシュする

- **決定**: `MindMapCanvas` の `nodes`/`edges` を組み立てる `useMemo` は、`useRef` に保持した「前回生成したオブジェクトのidキーMap」を参照し、内容（ノードは `content`/`position`/`selected`、エッジは `source`/`target`/`sourceHandle`/`targetHandle`/`label`）が変わっていない要素は新しいオブジェクトを作らず前回と同一の参照を返す。
- **背景**: `currentMap.nodes`/`currentMap.edges` はイミュータブルに更新されるため、ストアが変わるたび（1文字のキー入力、ドラッグの毎フレーム、選択変更を含む）に配列全体を作り直していた。React Flowはノード/エッジのオブジェクト参照の同一性で `memo` 化されたカスタムノード/エッジの再レンダーを判定するため、無関係なノードまで毎回再生成・再レンダーされ、ノード数が多いマップほどキー入力やドラッグの追従が重くなっていた。
- **採用理由**: ノードID/エッジIDをキーにした前回オブジェクトとの値比較 + キャッシュMapの総入れ替え（削除されたノードのエントリを引き継がない）という単純な実装で、React標準のメモ化パターン（`React.memo` + props参照同一性）とかみ合う形で再レンダーを抑制できる。追加依存なし。
- **不採用案とその理由**:
  - **`nodes`/`edges` 全体を `useMemo` の依存配列だけで再利用可否を判定する**: 依存配列 (`currentMap` 全体) はテキスト入力のたびに参照が変わるため、結局毎回作り直しになり効果がない（今回の問題そのもの）。
  - **`React.memo` の第2引数（カスタム比較関数）でCustomNode側の再レンダーを抑制する**: React Flow内部が新しいnodesオブジェクト配列を受け取った時点で内部状態の差分計算・再描画処理が走るため、根本原因（配列/オブジェクトの使い捨て生成）を解決しない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（現状の方式を維持）。

## 17. BubbleMenuの有効/無効切り替えはReactのマウント管理ではなくProseMirrorプラグインの登録/解除で行う

- **決定**: `CustomNode` 内のBubbleMenu（テキスト選択時の書式バー）は、`@tiptap/react` の `<BubbleMenu>` コンポーネントをそのまま使わず、中身を入れる `<div>` は常時マウントしたまま、`@tiptap/extension-bubble-menu` が公開する `BubbleMenuPlugin` を `editor.registerPlugin()` / `unregisterPlugin()` で直接呼び出し、`isEditing` に応じて登録・解除を切り替える自前実装にした。
- **背景**: 当初「`isEditing` のときだけ `<BubbleMenu>` をレンダーする」（`{isEditing && <BubbleMenu>...</BubbleMenu>}`）という素朴な条件付きレンダーを実装したところ、`isEditing` が `false` に戻った瞬間に `Failed to execute 'removeChild' on 'Node': The node to be removed is not a child of this node.` という例外が発生し、アプリ全体（Reactツリー）がクラッシュした。原因は `@tiptap/extension-bubble-menu` の内部実装（`BubbleMenuView`）が、プラグイン登録時に中身の `<div>` の実DOMノードを `element.remove()` で親から切り離し、表示時には tippy.js が生成するポップアップ側へ実DOMごと再親子付けする点にある。Reactの仮想DOMは「その `<div>` は自分が描画した親の子である」という前提のまま管理を続けるため、Reactが自前でアンマウント時に `removeChild` しようとした瞬間、実際のDOM上の親子関係とズレて例外になる。
- **採用理由**: 中身の `<div>` をReactのマウント/アンマウント管理から外し常時マウントさせておくことで、tippy.js側の実DOM移動とReactの仮想DOM管理が競合しなくなる。プラグインの登録・解除だけを `isEditing` で切り替えれば、実質的に「編集中の1ノードだけがtippyインスタンスを持つ」という当初の目的（全ノード分のtippyインスタンスが常時生き続けることによる負荷を避ける）を安全に達成できる。`editor: Editor | null` prop的なオフィシャルな無効化手段（`<BubbleMenu editor={null}>`）も検討したが、`menuEditor` が空になるたびに `console.warn` が出る実装になっており、大量のノードで頻繁に発生させたくないため見送った。
- **不採用案とその理由**:
  - **`<BubbleMenu>` をそのまま `isEditing` で条件付きレンダーする**: 上記の通りクラッシュする。
  - **`<BubbleMenu editor={isEditing ? editor : null}>` として要素自体は常時レンダーしつつeditor propだけ切り替える**: クラッシュは避けられるが、`editor` が `null` になるたび公式コンポーネント内部で `console.warn` が発生する。ノード数分・編集終了のたびに警告が出るため見送った。
- **表示上の注意**: 中身の `<div>` はプラグイン未登録中（編集中でない間）は `hidden`（`display:none`）クラスを付与している。`visibility:hidden` のままだとボタン行の高さぶんレイアウトスペースが常にノード内に残ってしまうため。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: `@tiptap/extension-bubble-menu` の将来バージョンで、Reactコンポーネントとしての安全なマウント/アンマウントが公式サポートされた場合は、自前実装をやめて標準の `<BubbleMenu>` に戻すことを検討する。

## 18. マップ初期化のStrictMode二重実行対策は `useRef` の初期化済みフラグ

- **決定**: `MindMapCanvas` のマップ初期化 `useEffect`（localStorageドラフト復元 → 初回訪問ならデフォルトマップ → それ以外は新規マップ、の分岐）の先頭で `useRef(false)` の初期化済みフラグをチェックし、既に初期化済みなら何もしない冪等な実装にした。
- **背景**: 開発時の React StrictMode は、副作用を検出する目的でマウント時のeffectを「実行 → クリーンアップ → 再実行」と連続で2回呼び出す。このeffectはクリーンアップ関数を返さないため、2回とも本体が素通しで実行される。1回目の実行で `markAsVisited()`（`localStorage` への同期書き込み）が先に走ってしまうため、2回目の実行時点では `isFirstVisit()` が既に `false` を返し、`createNewMap()`（"Root Node" 1個の空マップ）分岐に落ちる。Zustandの `set()` は同期的に反映されるため、2回目の呼び出しが1回目の結果（7ノードのデフォルトマップ）を上書きし、最終的に初回訪問時のデフォルトマップ表示が壊れていた（本番ビルドではStrictModeの二重実行がないため症状は出ない）。
- **採用理由**: `useRef` はコンポーネントインスタンスに閉じたシンプルな対策で、他の状態管理を汚さない。StrictModeの2回目の呼び出しをこのeffect内だけで確実にスキップできる。
- **不採用案とその理由**:
  - **モジュールスコープの変数でフラグ管理する**: コンポーネントをまたいで状態を持つため、テストやコンポーネントの複数インスタンス化（通常は起きないが）で意図しない影響が出うる。`MindMapCanvas` は1インスタンスしか存在しないため `useRef` で十分であり、より局所的な対策を優先した。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（現状の方式を維持）。

## 19. `onUpdate` は再シリアライズ結果が既存contentと無変化なら無視する

- **決定**: `CustomNode` のTiptap `onUpdate` コールバックの先頭で、`JSON.stringify(editor.getJSON())` の結果を現在の `data.content` と文字列比較し、完全一致する場合は `updateNodeContent`（延いては `saveToHistory`）の呼び出し自体をスキップするようにした。
- **背景**: 調査の過程で、ノードのマウント時（ユーザーが一切操作していない時点）にTiptap/ProseMirror側の初期化処理（スキーマ正規化など、正確な発生源は特定できていない）によって `onUpdate` が発火し、しかも再シリアライズした内容は既存の `data.content` と完全に一致する（＝内容としては無変化）ことを確認した。この無変化な `onUpdate` が `recordHistory=true` の状態（編集セッションの最初の変更）で発火すると、ノード作成直後に `addNode` 自身が積む履歴に加えてもう1回（開発時のReact StrictModeでは実質2〜3回）履歴が積まれ、「ダブルクリックでノードを1個作っただけなのにUndoを複数回押さないと元に戻らない」という不具合の原因になっていた（Tabキーでの子ノード作成でも同様に発生することを確認済み）。
- **採用理由**: 「内容が変わっていないなら履歴も更新もしない」というガードは、Undo/Redoの意味論（履歴は意味のある変更の単位で積む）そのものであり副作用がない。ユーザーの実際の編集（内容が変わる操作）を誤って無視することは原理的に起こらない（ガード条件が「完全一致」のときだけ発火するため）。ノード作成直後の履歴が1回で済むようになり、初回マウント時に無条件で `isDirty: true` になる・下書き保存が走るといった副作用も合わせて解消される。
- **不採用案とその理由**:
  - **発火元の特定・抑制（Tiptap拡張の設定変更等でスキーマ正規化自体を止める）**: 発火源を明確に特定できておらず、`StarterKit` 内のどの拡張機能の挙動に依存しているか不明なまま設定を変更するのはリスクが高い。今回のno-opガードは発火源によらず症状を確実に防げるため、より低リスクな対策を優先した。
  - **`addNode` 側で新規ノード作成直後の最初の `onUpdate` だけを別フラグで無視する**: 新規作成時に限定した特別扱いになり、Tabキー作成・ダブルクリック作成など複数の作成経路すべてに同じ特別扱いを配線する必要があり実装が煩雑になる。今回のガードは発火経路によらず一箇所で効くため、より汎用的。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 将来、意図的に「内容が同じでも編集アクションとして履歴に積みたい」ユースケース（今のところ想定なし）が出てきた場合に再検討する。

## 20. 編集中のEnter/Tabの挙動: デスクトップはEnter=確定+兄弟作成、タッチはEnter=改行

- **決定（初版。第2バッチで反転済み。下記「改訂」参照）**: ノード編集中のキー操作を次のように統一する。
  - **Tab**: 環境を問わず「編集確定＋子ノード作成」（新ノードはarmed。マインドマップ標準の階層操作）。
  - **Enter（非タッチ環境）**: 「編集確定＋兄弟ノード作成」（新ノードはarmed）。
  - **Enter（タッチ環境）**: 改行のまま（ノードを増やさない）。判定は `wasLastInteractionTouch()`（直近のポインタ操作がタッチ由来だったか）で行う。
  - **Shift+Enter**: 環境を問わず常に改行（Tiptapのデフォルト処理に委ねる）。
  - **IME変換確定のEnter**（`event.isComposing` または `keyCode === 229`）: 編集終了・ノード作成のトリガーにはしない（変換確定のためのEnterをそのまま消費してしまうと、変換を終えただけでノードが作られてしまう）。
- **採用理由（初版）**:
  - デスクトップでは「Enterで確定して次を作る」という高速な連続入力が主要な操作感（他の多くのアウトライナー/マインドマップアプリの慣習）であり、それを優先した。
  - **タッチ環境でEnter=兄弟ノード作成にしてしまうと、スマホのソフトキーボードで文章中に改行を入れる手段が失われる**（Shift+Enterはソフトキーボード上で押しづらい・存在しないことが多い）。ノード作成はハンドルドラッグや長押しメニュー等の別手段で引き続き可能なため、タッチ環境ではEnterの意味をあえて「改行」に固定した。
- **不採用案とその理由（初版）**:
  - **タッチ環境でもEnter=兄弟ノード作成に統一する**: スマホで長文をノードに入力する際に改行できなくなり、実用上の後退が大きい。

### 改訂（第2バッチ）: デスクトップの編集中Enterは「確定のみ」に反転（兄弟作成はしない）

- **決定**: デスクトップの編集中`Enter`（非Shift）の挙動を「編集確定＋兄弟ノード作成」から**「編集確定のみ（armedへ戻る）」**に変更した。弟ノード作成は行わない。続けて`Enter`を押す（armed状態でのEnter）と、`useKeyboardShortcuts`側の`createSiblingNode`が発火して弟ノードが作成される（既存のキーバインド`createSiblingNode: 'Enter'`をそのまま使う。armed状態のEnterはこの反転以前から弟ノード作成に割り当て済みだった）。タッチ環境のEnter（改行のまま）・Tab（子作成）・Shift+Tab（親作成）・Shift+Enter（改行）は変更なし。
- **背景（なぜ反転したか）**: 初版の「確定+兄弟作成を1回のEnterで行う」仕様は、ユーザーが**確定だけしたい**（次のノードを作るつもりはなく、単に入力を終えたい）場面でも常に兄弟ノードが作られてしまい、不要なノードができてから都度削除する手間が生じていた。「確定」と「作成」を意味的に別のアクションとして分離し、作成したい場合だけ追加でEnterを押す（＝2回Enterで1個作成、というアウトライナー的操作感）方が意図と一致する、というユーザー判断による。
- **不採用案とその理由**:
  - **初版のまま（確定+作成を1回のEnterで統一）を維持する**: 上記の「確定だけしたい場面で不要なノードができる」問題が残る。
  - **確定+作成のままにしつつ、作成したノードが空なら次のEnter/Escapeで自動的に削除する**: 「空ノードは自動削除される」という別の暗黙ルールを追加することになり、ユーザーが意図的に空ノードを一時的に残したいケース（後で書く用のプレースホルダ等）と衝突する。単純に「確定」と「作成」を分離する方が挙動として素直。
- **影響**: `CustomNode.tsx`の`editorProps.handleKeyDown`から`createSiblingNode(id)`呼び出しを削除（`setEditingNodeId(null)`のみ）。これに伴い`CustomNode`内で`createSiblingNode`が未使用になったため`useNodeCreation()`の分割代入からも削除した（フック自体・armed経由の呼び出しは維持）。`e2e/editing-keys.mjs`の`testEnterConfirmsAndCreatesSibling`をこの反転後の挙動（1回目のEnterは確定のみでノード数不変、armedになった後の2回目のEnterで兄弟ノードが1個作成される）に更新した。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。

### 再改訂: 編集中のEnterは「改行」に統一（デスクトップも改行）

- **決定**: 編集中`Enter`（非Shift・非IME）の挙動を、上の「確定のみ」からさらに変更し、**デスクトップ・タッチとも「改行」（Tiptapのデフォルト処理に委ねる）**に統一した。編集中Enterでは編集確定もノード作成もしない。弟ノード作成は、`Escape`/`Tab`等で編集を終えて**armed（ノード選択）状態にしてから`Enter`**を押すと`useKeyboardShortcuts`側の`createSiblingNode`で発火する（キーバインド`createSiblingNode: 'Enter'`はそのまま）。Shift+Enter（改行）・Tab（子作成）・Shift+Tab（親作成）は変更なし。
- **背景（なぜさらに変えたか）**: 「確定のみ」でも、ノード内で改行を入れたい（1ノードに複数行のテキストを書きたい）場面で、デスクトップだと編集中Enterが確定になってしまい改行できなかった。ノード内改行を最優先するというユーザー判断により、編集中Enterを素直に「改行」に固定した。これによりデスクトップとタッチで編集中Enterの意味が一致し、挙動もシンプルになる。
- **不採用案とその理由**:
  - **「確定のみ」を維持**: ノード内改行の手段がデスクトップで失われる（Shift+Enterはあるが、一般的なテキスト入力の直感に反する）。
  - **Enter=確定、別キー（例 `Ctrl+Enter`）=改行**: 改行のための追加キーを覚える必要があり、「Enter＝改行」という一般的な編集の直感から外れる。
- **影響**: `CustomNode.tsx`の`editorProps.handleKeyDown`の編集中Enter分岐を丸ごと削除し、Enterは他キー同様 `return false` でTiptapへ委ねるだけにした（`wasLastInteractionTouch()`分岐も不要になり削除。ただし同関数は`armed`判定で引き続き使用）。`e2e/editing-keys.mjs`の該当テストを`testEnterInsertsNewlineThenSiblingFromArmed`（編集中Enter＝改行で編集継続、Escape→armed→Enterで弟ノード1個作成）に更新。README「編集中のEnter/Tab」表もEnter＝改行に更新。

## 21. キャンバス上のイベントは document のキャプチャフェーズで拾う（バブルフェーズでは効かない）

- **決定**: `ContextMenu`（右クリックメニュー）・`Toolbar`（ファイルメニュー/モバイルの⋮メニュー）の「メニュー外クリックで閉じる」処理は、`document.addEventListener('mousedown', handler, { capture: true })` のようにキャプチャフェーズで登録する。バブルフェーズ（`capture: false`、デフォルト）では登録しない。
- **背景（過去に実際に踏んだ不具合）**: React Flowは内部で d3-zoom / d3-drag を使ってパン・ズーム・ノードドラッグを実装しており、これらはキャンバス上での `mousedown` イベントに対して `stopImmediatePropagation` 等でイベント伝播を止める。そのため、「外側クリックで閉じる」処理をバブルフェーズの `document` リスナーで実装すると、**キャンバスの空白部分をクリックしてもイベントが `document` まで届かず、メニューが閉じない**という不具合になる。この問題は `ContextMenu` と `Toolbar` の両方で個別に発生し、同じ原因・同じ対策（キャプチャフェーズ化）で解決した経緯がある。
- **採用理由**: キャプチャフェーズは「document → 対象要素」の順で発火するため、d3側が対象要素（キャンバス）の段階で行う `stopPropagation`/`stopImmediatePropagation` より先にdocument側のリスナーが実行され、影響を受けない。
- **不採用案とその理由**:
  - **バブルフェーズのままキャンバス側に個別のクリックハンドラを追加して閉じる**: メニューを閉じる必要がある「外側」はキャンバスだけでなくサイドバー・他のUI領域も含むため、閉じたい対象ごとに個別配線が必要になり保守性が低い。documentのキャプチャフェーズ1箇所に集約する方が汎用的。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（新しく「外側クリックで閉じる」UIを追加する際は、この実装（`ContextMenu.tsx`・`Toolbar.tsx`の`useClickOutside`）を再利用し、同じ罠を再度踏まないこと）。

## 22. React Flowの `disableKeyboardA11y` は有効化する（アプリ独自ナビゲーションとの二重化解消）

- **決定**: `<ReactFlow disableKeyboardA11y={true} />` とし、React Flow標準のキーボードアクセシビリティ機能（ノードDOMがフォーカスを持っている状態で矢印キーを押すと、選択中ノードそのものがその方向へ移動する機能）を無効化する。
- **背景**: armed-focus方式の採用により、選択中ノードのTiptapエディタ（`.ProseMirror`、React Flowのノードのラッパー要素の子孫）に常時フォーカスが当たるようになった。これにより、React Flow標準の「フォーカスされたノードの矢印キー操作」機能が常時有効な状態と衝突し、本来「隣接ノードへ選択を移動する」ためのアプリ独自の矢印キーナビゲーション（`useKeyboardShortcuts` の `selectParent`/`selectChild`/`selectPrevSibling`/`selectNextSibling`）と二重に働いて、**矢印キーを押すたびにノードそのものの位置が動いてしまう**不具合になっていた。
- **採用理由**: ノード移動のキーボード操作はアプリ独自ナビゲーション（選択移動）に一本化されており、React Flow標準のノード移動機能は使っていない。フラグ1つで衝突を根本から解消でき、副作用もない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（armed-focus方式を維持する限り、このフラグも維持する）。

## 23. E2Eテストは素のplaywright + 自前ランナー（`@playwright/test`は不採用）

## 24. エッジの単独クリック選択を廃止し「クリック=ラベル編集+✕」に一本化、複数選択はShift+クリックのみ

- **決定**:
  - エッジの**単独クリック**（Shiftなし）は、クリックした位置（パスの端・中央・ラベルチップのどこでも）に関わらず、常に「ラベル編集input + ✕（削除）ボタン」を一体で開く。✕なしの編集inputだけが表示されるケース、および編集モードに入らず選択状態だけになるケースの両方を廃止した。
  - エッジの選択状態（Delete一括削除・複数選択ハイライトの対象）は **Shift+クリックでのトグル**でのみ成立する（`uiStore`の`selectedEdgeIds: string[]`・`toggleEdgeSelection`）。旧`selectedEdgeId`（単独選択、ノード選択と排他）は廃止。
  - ノードもエッジも同じ選択モデルに統一した: 通常クリック（ノードのみ。エッジに「通常クリックでの選択」は無い）は単独選択で他の選択を全クリア、Shift+クリックはノード・エッジを問わずトグルで追加/除外し、ノード選択とエッジ選択は**混在を許す**（クリアし合わない）。
  - 選択中のノード・エッジをDelete/Backspaceでまとめて削除する`mapStore.deleteNodesAndEdges(nodeIds, edgeIds)`を追加し、`saveToHistory()`を1回だけ呼ぶことで、複数要素を消してもUndo 1回で全部復元される。
- **背景**: 前バッチで「エッジクリックで選択状態にしてDeleteキーで削除できる」機能を実装したが、ユーザーの実利用でDeleteキーがエッジを削除しない不具合が発生した。原因は、エッジ**中央**（ラベルチップの表示位置）をクリックすると、そこにあるラベル編集input（✕ボタンなし版）にフォーカスが移ってしまい、その状態でDeleteキーを押すとテキスト編集（1文字削除）として処理され、アプリ全体のキーボードショートカット（`useKeyboardShortcuts`のwindowレベルハンドラ）まで届かなかったこと。加えて、エッジの**端**をクリックした場合は「✕なしの編集input」、**中央**をクリックした場合は「selected状態＋✕付きチップ」という、クリック位置によって見た目・できることが変わる一貫性の無さもユーザー体験上の問題だった。
- **採用理由**:
  - 「クリックすれば常に編集+削除ができる」という一貫した振る舞いにすることで、クリック位置によって挙動が変わる混乱を無くした。✕ボタンを常にinputとセットで表示するため、「選択してからDelete」という編集inputにフォーカスが奪われがちな操作手順に頼らず、✕ボタンを直接クリックすれば確実に削除できる。
  - 複数選択・一括削除というニーズ（ノードは既にShift+クリックの複数選択を持っていた）に対して、エッジもShift+クリックで同じモデルに揃えることで、ユーザーが覚えるルールを1つに減らした。
- **不採用案とその理由**:
  - **単独クリック時のフォーカス奪取だけを解消する（✕ボタンの表示条件やクリック挙動はそのまま）**: 中央クリックでinputにフォーカスが移ること自体は編集機能として必要なため、フォーカス奪取だけを避けようとすると「クリックしても編集モードに入らない」体験になり本末転倒。加えて「端と中央で見た目が違う」問題は残ったままになる。
  - **Delete処理側で「フォーカスがinput内でもエッジ削除を優先する」ような特殊分岐を入れる**: input内でのテキスト編集用Deleteと、エッジ削除用Deleteの意図をキーイベントから区別する信頼できる方法が無く、通常のテキスト編集（ラベル文字の削除）ができなくなる副作用がある。
- **実装上の既知の罠（今後同じ罠を踏まないための記録）**:
  - **React FlowのBaseEdgeはデフォルトで`interactionWidth=20`の当たり判定用パス（`react-flow__edge-interaction`）を自動生成し、自前で用意した当たり判定パスの後に重ねて描画される。** SVGは後に描画した要素が手前（クリックを受け取る側）になるため、自前パスに`onClick`を付けても、BaseEdgeの自動生成パスがクリックを奪ってしまい発火しないことを実装中に確認した。`<BaseEdge interactionWidth={0} />`で自動生成を無効化し、自前パスをBaseEdgeの可視パスより**後**（DOM順で後＝描画上は手前）に置くことで解決した（`src/components/Editor/CustomEdge.tsx`）。
  - **React（v17以降）のonClickはブラウザのネイティブclickイベントがReactのルートコンテナまで実際に届いて初めて発火する。** 特定の子要素にonClickを付けても、その要素より手前（paint順で後）に別の要素が重なっていると、ネイティブイベント自体がその別要素で止まり（正確にはヒットテストで別要素が対象になり）、Reactの合成イベントディスパッチ自体が発生しない。「onClickを付けた要素がDOM/SVGの描画順で確実に最前面か」を常に確認すること。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: なし（この選択モデルを維持する）。BaseEdgeの`interactionWidth`のデフォルト挙動が将来のバージョンで変わった場合は、この対処（`interactionWidth={0}`＋描画順）の要否を見直す。

## 25. 整列のキーバインド化（`Ctrl+Shift+L`）と、選択ノードのみの部分整列

- **決定**:
  - 整列（`useAutoLayout.applyLayout`）にキーバインド`autoLayout`を追加し、デフォルトキーは**`Ctrl+Shift+L`**とする。
  - `applyLayout(nodeIds?: string[])`のように、対象ノードIDの配列を明示的に渡せるシグネチャに変更した。旧実装は`useAutoLayout`内部で`useUIStore`から選択状態を直接読んでいたが、呼び出し側（キーバインド・ツールバーボタン）が「今どのノードが選択されているか」を渡す形にした。
  - `nodeIds`が**2件以上**のとき: 対象ノードと、**両端が対象ノードに含まれるエッジのみ**でELKグラフを構築してレイアウトする（対象外ノードへつながるエッジは含めない）。レイアウト結果は、**元の対象ノード群の外接矩形の左上**が**整列前の外接矩形の左上**と一致するように平行移動してから反映する。`fitView`は呼ばない。非対象ノードの位置は一切変更しない。
  - `nodeIds`が1件以下（未指定含む）のときは、従来どおりマップ全体を整列する。
  - キーバインドのハンドラ（`useKeyboardShortcuts`のautoLayoutケース）とツールバーの「整列」ボタン（デスクトップ・モバイル⋮メニュー共通の`handleAutoLayout`）は、どちらも`selectedNodeIds.length >= 2 ? applyLayout(selectedNodeIds) : applyLayout()`という同じ分岐で呼び出し、キー操作とボタン操作で挙動が食い違わないようにした。
  - 整列は全体・部分のどちらも`saveToHistory()`を実行前に1回だけ呼ぶ。旧実装は`saveToHistory()`を一切呼んでおらず、整列がUndo対象になっていなかった（バグ）。これを修正し、整列はUndo 1回で整列前の状態に戻るようにした。
- **背景・不採用案とその理由**:
  - **キー`Ctrl+L`は使えない**: ChromeもFirefoxも`Ctrl+L`をアドレスバーへのフォーカス移動に予約しており、Webページ側の`keydown`ハンドラで`event.preventDefault()`しても奪えない（ブラウザネイティブのショートカットとして扱われる）。そのため`Ctrl+Shift+L`を採用した。`Ctrl+Shift+`の並びで他に予約されている組み合わせ（`+N`=シークレットウィンドウ、`+T`=閉じたタブを開く、`+Delete`=閲覧履歴消去等）を避けた上で選定している。
  - **キー表記の大文字小文字**: `keybindStore.normalizeKey`は`Ctrl`/`Shift`/`Alt`の接頭辞＋`event.key`の単純な文字列結合で、大文字小文字を区別する完全一致比較（`getActionForKey`）で照合される。実ブラウザでは、Shiftを押しながら文字キーを押すと`event.key`はそのキーの**大文字**（例: `L`）になる。そのため`defaultKeybinds.autoLayout`は`'Ctrl+Shift+L'`（大文字）で登録する必要がある（既存の`redo: 'Ctrl+Shift+z'`は小文字表記で、実機の物理キーボードと一致しない潜在バグだった。詳細は次項。**その後、`getActionForKey`の照合を1文字キーについて大文字小文字非依存にする修正（`canonicalizeKeybind`）で解決済み**）。
  - **既存の`redo: 'Ctrl+Shift+z'`（小文字）との整合性について**: 調査の結果、この小文字表記は実機の物理キーボードでの`Shift+Z`押下（`event.key === 'Z'`大文字）とは一致しない可能性が高いことが分かった。にもかかわらず既存のE2Eテスト（`e2e/text-undo-redo.mjs`）がこれまでPASSしていたのは、Playwrightの`page.keyboard.press('Control+Shift+z')`が、実ブラウザのShiftによる大文字変換を再現せず、**呼び出し時に指定した文字ケースをそのまま`event.key`として発火する**という、Playwright固有の挙動によるものだと判明した（`chromium`をCDP経由で操作して`keydown`イベントのペイロードを直接ログ出力して確認済み）。つまりE2Eでの「動作確認」と実ブラウザでの実キー入力が一致しない既存の潜在バグだった。**この問題は本タスクの直後に、`keybindStore.getActionForKey`の照合を修正して解決した**: 比較時に両辺を`canonicalizeKeybind`（バインド文字列の最後のトークンが1文字キーの場合のみ小文字化。`ArrowUp`/`Tab`等の複数文字キーは不変）に通すことで、保存表記の大文字小文字（過去のデフォルト値や localStorage に永続化済みのユーザー設定を含む）によらず一致するようにした。保存済みデータの書き換え（マイグレーション）を伴わないため、既存ユーザーの設定を壊さない。ヘルプモーダルの競合検出も`getActionForKey`経由のため同時に正しくなる。**E2Eのキーボードテストを書く際は、Shift併用の文字キーを実機同様に大文字で指定すること**（例: `press('Control+Shift+L')`）。新規追加の`autoLayout`は、この落とし穴を踏まないよう、実際のShift押下時の大文字化に合わせて`'Ctrl+Shift+L'`（大文字）で登録し、E2Eテスト（`e2e/align-keybind.mjs`）側も`page.keyboard.press('Control+Shift+L')`と大文字で明示的に指定することで、テストの見かけ上のPASSと実ブラウザでの実際の動作を一致させている。
  - **部分整列のエッジ対象を「両端が選択ノードに含まれるエッジのみ」にした**: 旧実装（本タスク前のコード）は「選択ノードのいずれかを含むエッジ」（片端のみでも対象）を拾っており、ELKのレイアウト対象に非選択の隣接ノードまで含めてしまっていた（最終的な位置更新は選択ノードのみに絞っていたため見た目のバグは無かったが、非選択ノードの存在が選択ノードのレイアウト計算に影響し、意図と異なる配置になり得た）。両端が選択ノードに含まれるエッジのみに絞ることで、「選択ノードだけの独立したサブグラフ」として素直にレイアウトされるようにした。
  - **アンカーを「外接矩形の左上」にした**: 旧実装は`selectedIds`の中で`currentMap.nodes`の並び順で最初に見つかったノード1個の位置を基準にオフセットを計算しており、その基準ノードがどのノードになるかは選択順ではなく元のノード配列順に依存する分かりにくい挙動だった。外接矩形（対象ノードの`position`の`min(x)`, `min(y)`）の左上を基準にすることで、「選択したまとまりが、選択した場所でその場整列される」という直感的な挙動にした。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: ブラウザ側で`Ctrl+L`のオーバーライドが可能になった場合でも、既にユーザーに`Ctrl+Shift+L`が周知されるため変更しない。キーバインド照合を触る際は、Playwrightのキー入力とブラウザ実機の差異（上記）に注意すること。

## 26. 整列は現在配置をヒントに使う差分的レイアウト（ELKのINTERACTIVE戦略）

- **決定**: `calculateLayout`（`src/utils/layout.ts`）でELKグラフの各childに現在のノード座標（`x`/`y`）を渡し、layeredアルゴリズムの3フェーズの戦略を以下に変更する。
  - `elk.layered.cycleBreaking.strategy`: `GREEDY` → **`INTERACTIVE`**（循環エッジのどちらを逆転させるかを現在座標から決める）
  - `elk.layered.layering.strategy`: 未指定（デフォルト`NETWORK_SIMPLEX`） → **`INTERACTIVE`**（レイヤー割り当てを現在位置に寄せる）
  - `elk.layered.crossingMinimization.strategy`: `LAYER_SWEEP` → **`INTERACTIVE`**（兄弟ノードの並び順を現在の左右/上下関係から初期化する）
  - `elk.layered.nodePlacement.strategy`は`BRANDES_KOEPF`のまま変更しない。
  - これにより整列（全体・部分とも）は「グラフ構造だけからゼロから最適配置を計算」ではなく「**現在の配置（階層・兄弟の並び順・循環エッジの向き）をなるべく保ったまま、間隔と階層を整える**」動作になる。
- **背景（解決した問題）**:
  1. エッジを1本追加して再整列すると全ノードが全く別の位置に組み変わり、差分的な編集に見えない。
  2. 兄弟ノードの左右/上下の並びが整列のたびに入れ替わる等、直感と異なる整列になる。
  - **原因**: 旧実装は現在位置をELKに一切渡していなかった。レイヤー割り当て・循環エッジの逆転方向（`GREEDY`）・兄弟順（`LAYER_SWEEP`）がすべて毎回グラフ構造だけから決め直されるため、同一グラフに対しては決定的（再実行しても差分ゼロ）だが、グラフがわずかに変わると全体が組み変わる。
- **実験による裏付け（2026-07、elkjs 0.9.3）**: 12ノード＋循環1つのテストグラフ（ツリー3分岐＋`a2→x→y→a`の循環、DOWN方向、ノード180×60、spacing 50/80）で「初回レイアウト→エッジ1本追加→再レイアウト」のノード移動量を比較した。

  | 追加エッジ | 旧方式（位置を渡さない） | 新方式（位置ヒント＋INTERACTIVE） |
  |---|---|---|
  | b1→c | 平均623px移動・全12ノードが移動 | 平均48px・移動5ノードのみ |
  | c2→x | 平均644px・全12ノード | 平均74px・4ノードのみ |
  | a1→b2 | 平均592px・11ノード | 平均150px・10ノード（ただし局所的な詰め直し） |

  兄弟ノード（ルート直下のa,b,c）の並び順も、旧方式はエッジ追加のたびに入れ替わった（b,c,a → a,b,c → c,a,b）のに対し、新方式では維持された。再現方法: 純Nodeスクリプトで`elkjs`に上記オプションを渡して`elk.layout`を2回呼び、位置差分を測るだけ（ブラウザ不要）。回帰テストとして`e2e/layout-stability.mjs`に恒久化している。
- **採用理由**:
  - この問題は「メンタルマップの保持」（Misue, Eades, Lai, Sugiyama "Layout Adjustment and the Mental Map", 1995）として知られる古典的テーマで、ELKのINTERACTIVE戦略群はまさにこの用途（既存配置を尊重した再レイアウト）のために用意されている（ELK本家=KIELERプロジェクトの対話的エディタで使われる方式）。商用では yEd (yFiles) の階層レイアウトの「Use Drawing as Sketch」（incrementalモード）が同じ思想の代表的な採用例。
  - 副次効果として、循環エッジの逆転方向が現在座標基準になるため、「ユーザーが下向きに描いたエッジが整列で上下反転する」という直感に反する動きも消える。
  - 手動でのノード配置もユーザーの意図の表明であり、整列がそれを壊さないことは本アプリの操作モデル（自由配置＋時々整列）に合う。
- **不採用案とその理由**:
  - **2モード方式（通常整列=差分的、Shift+整列=ゼロから完全再レイアウト）**: UI・キーバインド・ドキュメントが増える。差分的整列で困る場面（散らかった配置を一発で組み直したい等）がまだ実際に確認されていないため見送り。不満が出た場合の第一候補（下記「再検討の条件」参照）。
  - **初回整列のみゼロから、以降はINTERACTIVE**: 「そのマップで整列済みか」の状態管理が必要になり、同じ操作が状況によって違う結果になる分かりにくさがある。
  - **`elk.layered.considerModelOrder`（データ配列順ベースの安定化）**: 並び順をノード/エッジの作成順で固定する方式。実行間の安定性は得られるが、ユーザーが手で動かした配置を反映できないため、位置ヒント方式のほうが本アプリに合う。
  - **力学モデル（d3-force等のwarm start）への置き換え**: 差分安定性は得られるが、階層構造の表現が弱く、DOWN/RIGHTというレイアウト方向の概念とも合わない。
- **制限**: 現在の配置を尊重するため、手動で大きく散らかした状態から一発で「教科書的な」配置には整わない（散らかした配置の骨格が保たれる）。これは仕様であり、ユーザーの配置意図を壊さないことを優先した結果。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 「ゼロから綺麗に再レイアウトしたい」というニーズが実際に出たら、2モード方式（別操作としてのフル整列）を追加する。その場合、フル整列側の実装は本セクションの旧オプション（位置を渡さず`GREEDY`+`LAYER_SWEEP`、layering未指定）をそのまま使えばよい。
- **関連**: エッジの接続方向（右側の子/下側の子等）ごとにレイアウト方向を分けたいという要望への対応は [align-branch-layout.md](./align-branch-layout.md)（検討中・未決定）を参照。この決定（現在配置をヒントに使う差分的レイアウト）は学術的には「動的グラフ描画／メンタルマップの保持」という分野に対応する。分野全体の見取り図は [graph-drawing-primer.md](./graph-drawing-primer.md)（グラフ描画入門）を参照。

## 27. 「編集中ノードは常に選択中」の不変条件を選択セッターで強制する

- **決定**: `uiStore` の選択セッター（`setSelectedNodeId` / `toggleNodeSelection`）の中で、更新後の選択集合に `editingNodeId` が含まれなくなる場合は `editingNodeId` を `null` にする。これにより「`editingNodeId` に入っているノードは必ず選択中（`selectedNodeId` か `selectedNodeIds` のいずれかに含まれる）」という不変条件を UI ストア側で保証する。
- **背景（解決した問題）**: ノードの枠色は2つの独立した状態から描画されている。青枠＝React Flow の `selected`（`selectedNodeId`/`selectedNodeIds` 由来、`MindMapCanvas` の `nodes` useMemo で計算）、緑リング＝`isEditing`（`editingNodeId === id`、`CustomNode`）。両者に不変条件がなかったため、選択が編集中ノードから外れても `editingNodeId` が残り、**枠グレー（未選択）＋緑リング（編集中）**という中途半端な状態が発生していた。この状態のノードは `isEditing` が true のまま再フォーカスされず、単独クリックは `CustomNode` の `handleClick` の `if (!isEditing)` に阻まれて何も起きないため、「緑なのにテキスト編集も選択もできない」操作不能状態になりユーザーが混乱していた。
  - **再現手順**: (1) ノードAをダブルクリックで編集開始 → (2) `Escape`/`Enter`/`Tab` で確定せずに別ノードBをクリック → `onNodeClick`/`handleClick` が `setSelectedNodeId(B)` を呼ぶが `editingNodeId` はAのまま → Aが枠グレー＋緑リストに。Shift+クリックで編集中ノード自身を選択解除する（`toggleNodeSelection`）経路でも同様に発生する。
- **採用理由**: 「編集中に別の場所をクリックしたら編集を確定して選択が移る」は一般的なエディタ/キャンバスUIの挙動（blur=commit）であり、不変条件の強制はこのUXと一致する。表示側（`CustomNode`）で `isEditing && selected` のように緑リングだけ隠す案も考えたが、それだとストアの状態は不整合のまま（エディタは editable・フォーカス対象のまま）で、緑リングが消えるだけの別の分かりにくさが残る。状態の発生源（選択セッター）で断つのが根本解。
- **不採用案とその理由**:
  - **表示側で緑リングを `isEditing && selected` に絞るだけ**: 見た目のゴーストは消えるが `editingNodeId` の不整合（editable/フォーカス管理・`editorStore.activeEditor` への公開など）は残るため、対症療法。
  - **`CustomNode` の blur ハンドラで `setEditingNodeId(null)`**: armed-focus 方式では非編集の選択中ノードもエディタにフォーカスを当てており（§13）、フォーカス移動が頻繁に起きるため blur を編集終了トリガーにすると誤終了しやすい。選択状態の変化を基準にするほうが確実。
- **検証**: 上記再現手順（編集中に別ノードをクリック／編集中ノードをShift+クリックで解除）で緑リングが残らないことを確認する。既存の選択→編集の各経路（ダブルクリック、印字可能文字での編集開始、ハンドルドラッグでの新規ノード作成 `onConnectEnd`、Tab/Enterでの子・兄弟ノード作成）は「選択してから編集」の順でセッターを呼ぶため、不変条件の下でも従来どおり編集状態に入れる（`setSelectedNodeId` は同一ノードを選択する場合は `editingNodeId` を保つ）。
- **関連**: 枠色の状態遷移（グレー=未選択／青=選択中・armed／青+緑=編集中）と armed-focus 方式は §13 を参照。

## 29. `Shift+Enter`=兄ノード作成 / `Shift+Tab`=親ノード作成 を追加

- **決定**: 既存の `Enter`（弟ノード作成）・`Tab`（子ノード作成）の対称操作として、`Shift+Enter`=兄ノード作成、`Shift+Tab`=親ノード作成を追加した。兄ノードは弟（`Enter`）の逆方向に配置する（RIGHTレイアウト→上、DOWNレイアウト→左）。親ノード（`Shift+Tab`）も対称に、子（`Tab`）の逆方向に配置する（RIGHT→左、DOWN→上）。
- **編集中のShift+Enterは改行のまま維持**（デスクトップでノード内改行の手段を残すため。決定#20の「Shift+Enter=改行」を踏襲）。そのため兄ノード作成は非編集（armed・ノード選択中）状態でのみ、`useKeyboardShortcuts`（グローバルキーハンドラ）経由でのみ発火する。`CustomNode` の編集中Enter分岐は変更していない。
- **親ノード（`Shift+Tab`）は編集中も発火する**（`Tab`=子作成の対称）。`Tab` は改行等の別用途を持たないため、編集中に割り当てても既存capabilityの喪失がない。この対応にあわせて、`CustomNode.tsx` の編集中 `Tab` 分岐が `event.shiftKey` を見ておらず **`Shift+Tab` でも子ノード作成になってしまっていた既存の取りこぼし**も同時に修正した（`!event.shiftKey` の場合のみ子作成、`event.shiftKey` の場合は親作成に分岐）。
- **多重親の挿入仕様**: 対象ノードTに`Shift+Tab`したとき、新ノードNをTの親として挿入する。Tが複数の親P=[p1,p2,...]を持つ場合、Pはすべて新ノードNの親になり（p→Tエッジをすべてp→Nへ張り替え）、TはNの子になる（N→Tエッジを新規追加）。Tの子ノードはTにつけたまま（Tから出るエッジは一切触らない）。Tが親を持たない（ルート）場合はN→Tを足すだけでNが新ルートになる。これらのグラフ変更（ノード追加・N→T追加・P→Tの張り替え）は専用の`mapStore`アクション`insertParentNode`で1回の履歴エントリにまとめており、`Ctrl+Z`一回ですべて戻る。
- **既存ユーザーのlocalStorage補完**: `keybindStore`は`persist`（`name: 'mindmap-keybinds'`）で永続化されているため、既存ユーザーの保存済み`keybinds`には新アクション（`createParentNode`/`createOlderSiblingNode`）が存在しない。デフォルトの`merge`は`keybinds`オブジェクトを丸ごと置換してしまい新キーが欠落するため、`persist`のoptionsに`merge`を追加し、`keybinds: { ...defaultKeybinds, ...(persisted.keybinds ?? {}) }`の形で既存カスタマイズを保ちつつ新デフォルトを補完するようにした。
- **不採用案とその理由**:
  - **編集中のShift+Enterも兄作成にする（Enterと完全対称）**: デスクトップでノード内改行の手段が失われるため見送り（ユーザー判断）。将来Shift+Enterを兄作成に寄せたくなったら、代替の改行キー割当（例: `Ctrl+Enter`）とセットで再検討する。
- **検証**: 型チェック（`tsc -b`）・ESLintで確認。実ブラウザでのキー入力（Shift+Enter/Shift+Tabの実際の発火・IME変換への非干渉・複数親ノードでの張り替え挙動）はWSL環境では確認できないため、ユーザーによる実機（Windows/macOS）での手動確認が必要。
- **関連**: `Enter`=改行という編集中挙動の決定は #20、armed-focus方式・編集中キー処理の全体像は #13 を参照。
- **調整箇所**: キーバインド既定値・説明文 = [src/config/defaultKeybinds.ts](../src/config/defaultKeybinds.ts)、位置計算（オフセット量 `x±200`/`y±100`/`y-120`）= [src/hooks/useNodeCreation.ts](../src/hooks/useNodeCreation.ts) の `createOlderSiblingNode`/`createParentNode`、多重親の張り替えロジック = [src/stores/mapStore.ts](../src/stores/mapStore.ts) の `insertParentNode`。

## 30. 兄弟作成は対象の隣に局所挿入、親作成は挿入時に対象を1レイヤ外へ自動整列

- **背景**: #29 でのキーバインド追加時点では、兄弟作成（`Enter`/`Shift+Enter`）の配置は `adjustPositionToAvoidOverlap` で空くまでずらす方式だったため、兄弟が複数いると新ノードが兄弟グループの一番端に付いてしまっていた。また親作成（`Shift+Tab`）は新ノードNを対象Tの単純に隣（左/上）へ固定配置するだけで、Nが実際に属する階層（Tの元の親の子レイヤ）に見合った位置にならなかった。本エントリはキーバインドや発火条件は変えず、配置ジオメトリのみを改善する。
- **決定（兄弟作成）**: 新ノードは対象の「一番端」ではなく「すぐ隣（弟なら1つ後ろ、兄なら1つ前）」のスロットに挿入する。既存の兄弟のうち挿入位置より遠い側（押し出される側）だけを、そのサブツリーごと主軸方向に1スロット分平行移動する。対象ノード自身・挿入位置より近い側の兄弟・無関係なノードは一切動かさない。挿入間隔は隣接する兄弟との実際の間隔を使い、対象が兄弟グループの端（隣接する遠い側の兄弟がいない）の場合のみ既定値（`defaultGap`: RIGHTレイアウト=100/DOWNレイアウト=200）にフォールバックする。親を持たない対象（ルート等、兄弟グループが無い場合）は常に既定値を使う。
- **決定（親作成）**: 挿入後、新ノードNは対象Tの元のスロット（位置）をそのまま継承する。対象Tとその子孫（サブツリー全体）は、レイヤ軸方向に`layerGap`（RIGHTレイアウト=200/DOWNレイアウト=120、`createChildNode`の子オフセットと同値）だけ外側へ平行移動する。これにより新ノードNが「Tの元の親からTへ」という既存の階層1レイヤ分をそのまま引き継いだ自然な位置に収まる。
- **サブツリーの平行移動（両方に共通）**: 押し出す兄弟・外側へずらす対象は、いずれも子孫（子・孫…）を含めてサブツリーごと同じ量だけ平行移動する。子孫IDの列挙は新規ヘルパー `getDescendantIds`（[src/utils/graphTraversal.ts](../src/utils/graphTraversal.ts)、循環ガード付きBFS/DFS、対象自身は含まない）を使う。
- **1履歴エントリ化**: ノード追加・エッジ張り替え・複数ノードの位置移動を同一トランザクションとして扱うため、`mapStore` に新アクション `addNodeWithShifts`（ノード追加+任意の親エッジ+位置移動シフト配列を受け取る）を追加し、既存の `insertParentNode` にも第6引数 `shifts`（省略可、省略時は`[]`で従来どおり位置移動なし）を追加した。どちらも内部で `saveToHistory()` を1回だけ呼ぶため、`Ctrl+Z` 一回でノード追加・エッジ変更・シフトされた全ノードの位置が一括で元に戻る。
- **不採用案とその理由**:
  - **作成直後に非同期ELK整列（`useAutoLayout.applyLayout`）を呼んで整列させる**: (1) `applyLayout`はReact Flowの最新nodes/edgesをフックのstale closure越しに参照する可能性があり、直後の状態と食い違うリスクがある。(2) ELK側でも独自に`saveToHistory()`相当の処理が走るため、ノード作成と整列が別々の履歴エントリになり`Ctrl+Z`一回で戻らなくなる。(3) ELKの間隔は固定定数ベースで、ユーザーが手動で作った可変間隔の既存レイアウトを壊してしまう。これらの理由から、直接ジオメトリ計算で同期的に必要最低限の移動だけを行う方式を採用した。
- **検証**: 型チェック（`tsc -b`）・ESLint・`npm run build`で確認。実ブラウザでの実際のキー入力による兄弟複数時の局所挿入・サブツリー平行移動・親作成時のレイヤ整列・`Ctrl+Z`一回での巻き戻しは、WSL環境では確認できないためユーザーによる実機での手動確認が必要。
- **関連**: キーバインド自体の追加は #29。
- **調整箇所**: 兄弟の既定間隔 `defaultGap`（[src/hooks/useNodeCreation.ts](../src/hooks/useNodeCreation.ts) の `computeSiblingInsertion` 内、RIGHT=100/DOWN=200）、レイヤ間隔 `layerGap`（同ファイル `createParentNode` 内、RIGHT=200/DOWN=120）。

## 33. 既存接続間の新エッジは後勝ち

- **背景**: 2ノード間に既に接続がある状態で別のハンドル（例: 上下ハンドル接続への変更）を使って再度ドラッグ接続すると、何も起きず無反応に見える不具合になっていた。

- **不採用案とその理由**:
  - **従来通り無視する（現状維持）**: ユーザーが意図して別ハンドルへ繋ぎ直そうとしても無反応になり、混乱の原因になっていた。
  - **多重エッジを許容する（両方残す）**: 同じノード間に複数のエッジが重なって描画され、視覚的に見分けがつかなくなる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。

## 34. ツールバー中央タイトルは左右UI実測幅からmaxWidthをクランプ

- **決定**: `Toolbar`で左グループ・右グループ（デスクトップ/モバイルのうち表示中の方）の`offsetWidth`をResizeObserverで実測し、中央タイトルの`maxWidth`を`ツールバー幅 - 2*max(左幅, 右幅) - TITLE_SIDE_GAP(16px)`にクランプする。中央タイトルはウインドウ幅の中央基準（`absolute left-1/2 -translate-x-1/2`）の配置を維持したまま、その位置で許容される最大幅を制限する。ウインドウ幅・タイトル文言・言語切替（`currentMap?.name`、`i18n.language`の変化）で再計算する。
- **背景**: 従来はタイトルの`max-width`がツールバー全幅相当（`max-w-full`）だったため、タイトルが長い・ウインドウが狭い場合に左右のボタン群と重なって見えていた。

- **不採用案とその理由**:
  - **3カラムflexレイアウト（左/中央/右をflexアイテムにして中央の残り幅を使う）**: 中央カラムが「ウインドウ中央」ではなく「左右グループに挟まれた残り領域の中央」に配置されるようになり、左右グループの幅が違うと見た目の中心がウインドウ中央からずれてしまう。現状の「常にウインドウ中央基準」という見た目を変えたくないため不採用。
- **調整箇所**: `TITLE_SIDE_GAP`（[src/components/Editor/Toolbar.tsx](../src/components/Editor/Toolbar.tsx)冒頭、16px、左右の追加余白）。

## 41. ノード内リストはtypographyプラグイン不使用でスコープCSS対応

- **決定**: 箇条書き/番号付きリスト（`ul`/`ol`）がFormatToolbarのボタンで生成されても視覚的にマーカーが出ない不具合を、`@tailwindcss/typography`プラグインの導入ではなく、`index.css`にスコープしたCSS（`.ProseMirror ul/ol/li`）を追加する形で修正した。
- **背景（根本原因）**: `CustomNode`の`prose prose-sm prose-invert`クラスは、`tailwind.config.js`の`plugins: []`によりtypographyプラグインが入っていないため実際には何の効果も持たない。一方Tailwind preflightは`ul`/`ol`を`list-style:none; margin:0; padding:0`にリセットするため、リストはドキュメント構造としては正しく生成されるのにマーカー無しの平文に見えるだけだった。
- **採用理由**: typographyプラグインは見出し・引用・コードブロック等ノードでは使わない要素まで含む幅広いスタイルセットを持ち込む。今回必要なのはリストのマーカー表示だけなので、影響範囲を`.ProseMirror`配下に限定した数行のCSSで十分かつ安全（他のTailwindユーティリティとの衝突リスクが無い）。
- **不採用案とその理由**:

## 44. 手動でのノード作成間隔を実測サイズ＋sugiyama-ext定数（PRIMARY_GAP/SIBLING_GAP）に統一

- **決定**: `Enter`/`Shift+Enter`（兄弟ノード作成）・`Tab`（子ノード作成）で新規ノードを配置する際の間隔計算を、自動レイアウト「sugiyama-ext」（`src/utils/sugiyamaExtLayout.ts`）と同じ定数・同じ式に統一した。
  - `sugiyamaExtLayout.ts`の`PRIMARY_GAP`・`SIBLING_GAP`・`DEFAULT_NODE_WIDTH`・`DEFAULT_NODE_HEIGHT`をexportし、`useNodeCreation.ts`から共有する。
  - **子ノード作成（`Tab`、RIGHT/DOWN共通）**: 親ノードの実測primaryサイズ（React Flowの`node.measured`、無ければDEFAULT）＋`PRIMARY_GAP`だけ前方に配置する（`childPosition = parent.position + parentPrimary + PRIMARY_GAP`）。これにより親右端(下端)と子左端(上端)の間隔が親の幅（高さ）によらず常に`PRIMARY_GAP`で一定になる（sugiyama-extのforward配置と同じ式）。
  - **兄弟ノード作成（`Enter`/`Shift+Enter`）**: cross方向のオフセットを、従来の「最寄り兄弟までの距離 or 固定defaultGap」ではなく、`boxGap = 対象のcross実測サイズ/2 + SIBLING_GAP + 新規ノードのcrossサイズ/2`（sugiyama-extの兄弟サブツリー間隔の式と同一）に統一した。新規ノードは常に空ノードのため実測が無く、cross既定サイズ（RIGHT:`DEFAULT_NODE_HEIGHT`、DOWN:`DEFAULT_NODE_WIDTH`）を使う。押し出す（遠い側の）兄弟＋その子孫は従来通り同じdelta分だけ平行移動する（相互距離は保持され、対象↔新規ノードの間隔のみboxGapになる）。親を持たない対象（ルート等）もboxGapベースの間隔を使う。
- **背景**: 手動作成（`computeSiblingInsertion`の`defaultGap`固定値、`createChildNode`の`x+200`固定値等）と自動整列（sugiyama-ext）が別々の間隔基準を使っていたため、Enter連打で作った兄弟ノードをその後Alignすると間隔が変わってしまい、「手で作った直後の配置」と「整列後の配置」が一致しなかった。
- **採用理由**: 双方が同じ定数・同じ式を共有することで、手動作成した直後の配置がAlign後（葉ノードの場合）もほぼ動かなくなり、ユーザーが「整列するとレイアウトが崩れる」と感じる場面を減らせる。
- **不採用案とその理由**:
  - **手動作成後に自動的にAlignを呼ぶ**: §30で既に検討・不採用にした案と同じ理由（stale closureのリスク、履歴エントリが分かれてUndo一発で戻らなくなる、ユーザーの可変間隔レイアウトを壊す）で見送り。今回のように配置計算の式自体を合わせる方が安全。
  - **sugiyama-ext側の定数を手動作成用に複製する**: 値がズレるリスク（片方だけ変更して同期を忘れる）があるため、単一のソース（`sugiyamaExtLayout.ts`のexport）を共有する方式にした。
- **調整箇所**: `PRIMARY_GAP`/`SIBLING_GAP`/`DEFAULT_NODE_WIDTH`/`DEFAULT_NODE_HEIGHT`は引き続き`src/utils/sugiyamaExtLayout.ts`冒頭が単一のソース（[docs/tuning.md](./tuning.md)参照）。

## 45. Shift+ドラッグの矩形選択をReact Flowの`onSelectionChange`経由でuiStoreへ橋渡し（2件以上のみ反映）

- **決定**: React Flowの`onSelectionChange`コールバックをuiStoreの新規action `setMultiSelection(ids: string[])`へ橋渡しする。`MindMapCanvas`側のハンドラは、選択ノード数が**2件以上**のときだけ`setMultiSelection`を呼ぶ（1件以下は何もしない）。既に同一集合が選択されている場合もno-op（無限ループ防止）。`setMultiSelection`は他の複数選択action（`toggleNodeSelection`/`addNodesToSelection`）と同様、`selectedNodeId=null`・編集中ノードが選択集合に含まれなければ`editingNodeId=null`（不変条件§27の維持）・`selectedEdgeIds`は維持、というセマンティクスにした。
- **背景**: 本アプリの選択状態はuiStore独自管理（`selectedNodeId`/`selectedNodeIds`）で、React Flow内部の選択状態（各ノードの`selected`プロパティ）とは別系統。`onNodesChange`の`select`種別の変更は明示的に無視している（`MindMapCanvas`のコメント参照）ため、React Flow標準機能であるShift+ドラッグの矩形選択がuiStoreに一切反映されず、矩形選択でハイライトされたノードを`Delete`キーで削除できない不具合になっていた（`Delete`処理はuiStoreの`selectedNodeIds`を見るため）。
- **採用理由**: `onSelectionChange`はReact Flowが矩形選択・Shift+クリック等あらゆる内部選択変更で発火する標準コールバックのため、矩形選択専用の座標計算やヒットテストを自前実装する必要がない。
- **2件以上のみ反映する理由（不採用案との比較）**:
  - **1件・0件でも常に反映する**: 単一クリックは`CustomNode.handleClick`/`MindMapCanvas.onNodeClick`が既に`setSelectedNodeId`等で管理しており、React Flowの内部選択変更（クリックでも`onSelectionChange`は発火する）まで拾ってしまうと、同じクリックに対して2つのハンドラが競合して意図しない選択状態になるリスクがある。矩形選択は「2個以上まとめて選ぶ」操作のため2件以上に限定することで、単一選択系のロジックとの競合を避けつつ矩形選択のユースケースだけを確実にカバーできる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 単一ノードの矩形選択（1個だけを矩形で囲む操作）でも独自の見た目・挙動が必要になった場合は、1件のケースの扱いを再検討する。

## 46. モバイルのドキュメントスクロールを抑止（html/body非スクロール化＋#root=100dvh）

- **決定**: `index.css`で`html, body { height:100%; overflow:hidden; overscroll-behavior:none; }`とし、`body`の`min-height:100vh`を撤去、`#root`を`height:100vh; height:100dvh;`にした。ドキュメント（`html`/`body`）自体をスクロール不可にし、可視ビューポート高（`100dvh`）に`#root`を固定する。
- **背景（根本原因）**: `body`の`min-height:100vh`は、モバイルでURLバーの出入りにより変動する可視ビューポート（`100dvh`）より`100vh`の方が大きくなる場面があり、ドキュメント自体がスクロール可能になっていた。トップバー/左カラム（MapList）を触った際にこのドキュメントスクロールが発生すると、`height:100vh`固定の`#root`ごと上へずれ、`h-12`のトップバーが画面外へ消える不具合になっていた。
- **採用理由**: `overflow:hidden`でドキュメントそのものをスクロール不可にし、`#root`を可視ビューポート高（dvh）に固定することで、「ドキュメントがずれてトップバーが消える」経路自体を断てる。デスクトップは`100dvh≈100vh`のため実質的な影響がない。左カラム内のリスト等、要素ごとのスクロールは既存の`overflow-y-auto`領域内でそのまま機能する。
- **不採用案とその理由**:
  - **`#root`の`height`を`100vh`のまま維持し、トップバーに`position:sticky`を付与する**: ドキュメントスクロール自体は残るため、他の要素（React Flow Controls等）が同様にずれる問題が個別に再発しうる。ドキュメントレベルでスクロールを止める方が根本対策になる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: モバイルでソフトウェアキーボード表示時のレイアウト崩れ等、`overflow:hidden`が原因で新たな不具合が確認された場合に見直す（現状はWSL環境では実機確認ができないため、docs/testing.mdの手動確認チェックリストに追加した）。

## 47. ノードのコンテキストメニューは対象のDOM矩形（anchorRect）を基準に自己サイズ計測して配置する

- **調整箇所**: メニューと対象/ビューポート端の余白`CONTEXT_MENU_GAP`（`src/components/Editor/ContextMenu.tsx`冒頭、[docs/tuning.md](./tuning.md)参照）。

## 48. `elk-port-ext` を「ELK layered の忠実な再実装」に作り替え、旧実装を `elk-port-pava` として残す

- **決定**: 整列アルゴリズム `elk-port-ext`（`src/utils/elkPortExtLayout.ts`）を、**`elk-port`（elkjs本体）と同じ結果を出すことを目標とした再実装**に置き換えた。従来の `elk-port-ext`（座標割当をPAVAで解き、原点へ正規化しない版）は削除せず、**`elk-port-pava`（`src/utils/elkPortPavaLayout.ts`）という別方式として残し**、dev限定の比較UIに7つ目の選択肢として追加した。
- **背景**: 「なぜ `elk-port` と `elk-port-ext` で結果が変わるのか」という問いに対し、当時の `elk-port-ext` は「同じ枠組みを最小構成で自前実装したもの」であって**アルゴリズムそのものが複数箇所で違っていた**（座標割当がBrandes–Köpfではなく等調回帰、north/southポートをダミーではなくオフセットで近似、原点正規化をしない、連結成分を分けない）。そのため「ELKと違うのはELKというパッケージのせいなのか、実装上の選択のせいなのか」を切り分けられなかった。
- **採用理由**:
  - 忠実版を作ると、**`elk-port` の結果のうち何がアルゴリズムの必然で、何がELK固有の選択なのかが切り分けられる**。以降の改善は忠実版をベースラインにして「どのフェーズをどう変えると何が良くなるか」を1つずつ測れる。
  - elkjs（GWTコンパイル済みバンドル）を外せるので**実行時間が20倍速くなり**（1136ms → 55ms）、同期関数にできる。
  - ELKの内部処理（north/southポートのダミー化・成分パッキング・原点正規化）が可視化され、コードとして読める形で残る。
- **どこまで一致したか**: 43ケースで**ケース単位25/43が完全一致、ノード単位で73.3%が一致**。測定は `npm run layout:parity`（`scripts/layout-elk-parity.mjs`）で再現できる。指標も `elk-port` に寄った（交差 799→834、貫通 235→248、移動量 369→345、**兄弟順の反転率は 0.006 で完全一致**）。**この方式に限り「指標が良くなる」ことは再現失敗を意味する**点に注意。
- **ELKのソースを読む方針に改めた（当初は読まずに実挙動から逆算していた）**: 「改造しやすくするための再実装」という目的からは、中身を理解せずブラックボックスの出力に合わせるのは遠回りだった。ELK 0.9.1（EPL-2.0）の該当クラスを読み、**移植はせず**「どのクラスが何をしているか」を把握したうえで必要な処理だけをベタ書きしている（ELKの関数・データ型はimportせず、`ILayoutPhase`・`IGraphImporter`・spacingsプロバイダのような他アルゴリズム共通化のための抽象も持ち込まない）。定数は既定値がオプションの組み合わせで変わるため、実測でも裏を取って観測ケースを [align-algorithms.md](./align-algorithms.md) §6.0 に残した。
- **読んで初めて分かった最大の誤り**: `crossingMinimization.strategy=INTERACTIVE` のとき、ELKはバリセンタ掃引を行う `LayerSweepCrossingMinimizer` を**使わない**。選ばれるのは `InteractiveCrossingMinimizer` で、**各層を現在の座標で並べ替えるだけ、交差削減は一切しない**。「スギヤマ枠組みなら交差削減をするはず」という思い込みで掃引を実装していたため、交差が 799 → 563 と勝手に「良くなって」ELKから離れていた。同様に、Brandes–Köpf の4パスを平均する balanced 合成も、`favorStraightEdges` が `edgeRouting=ORTHOGONAL`（layeredの既定）で true になるため**この構成では使われない**（実行可能なパスのうち広がり最小の1つをそのまま採る）。
- **不採用案とその理由**:
  - **旧 `elk-port-ext` を削除して置き換えるだけにする**: 旧実装は多くの指標で `elk-port`・忠実版の両方を上回っており（交差 209 vs 563/799、貫通 52 vs 266/235、面積・移動量も最良に近い）、`sugiyama-ext` の対抗馬として最終決定に関わる候補だった。消すと比較UIの目的（どれを本番既定にするかを実際に触って決める）が損なわれる。git履歴からの復元は可能だが、「並べて見比べる」ことができなくなる。
  - **忠実版を新方式として追加し、`elk-port-ext` はそのままにする**: 名前と実態が合わなくなる。「ext＝ELKを拡張/再実装したもの」という語感は忠実版のほうが自然で、PAVAで解く版は `pava` のほうが中身を表す。
  - **ELKのソースを読まずに実挙動だけから逆算する**（当初の方針）: ブラックボックスの出力合わせでは「なぜそうなるか」が分からず、交差削減の有無のような根本的な取り違えに気づけなかった。改造の土台を作るのが目的なので、読んだうえで最小構成に書き下すほうが目的に合う。
  - **ELKのコードをそのまま移植する**: ライセンス（EPL-2.0）の扱いが面倒になるうえ、ELKの抽象化（フェーズのインターフェース・グラフのインポータ・spacingsプロバイダ等）ごと持ち込むことになり、「マイナーな変更がしにくい」という元の問題がそのまま残る。
- **既知の未実装差分**: 逆向きポート（`InvertedPortProcessor` 相当。RIGHT時に左面から出るエッジを前後の層のダミーで回り込ませる処理）は実装しておらず、流れ方向の面と同じ扱いにしている。残り27%の不一致の主因は Brandes–Köpf の圧縮まわりの細部（`insideBlockShift` 相当のブロック内オフセットを持っていない点など）。
- **調整箇所**: `elk-port-ext` の再現用定数（`src/utils/elkPortExtLayout.ts` 冒頭）と `elk-port-pava` のチューニング定数（`src/utils/elkPortPavaLayout.ts` 冒頭）。一覧は [tuning.md](./tuning.md)「整列アルゴリズム」。**前者は「好みで調整するつまみ」ではなく再現用の値**なので、変えるとELK再現度が落ちる。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 本番既定のアルゴリズムが確定した時点で、不採用側は [align-branch-layout.md](./align-branch-layout.md)「今後の運び」に従って削除する。`elk-port` を落とすなら `elk-port-ext` の存在意義（elkjs依存を外すための忠実版）も同時に消えるため、両方まとめて判断する。elkjsのバージョンを上げたときは `npm run layout:parity` で一致度が落ちていないかを確認する（落ちていればELK側の挙動が変わった証拠なので、対応するELKのソースを読み直して定数を再測定する）。参照したELKは 0.9.1（elkjs 0.9.3 が同梱するのは ELK 0.9.x で、完全に同一のリビジョンではない）。

## 49. `sugiyama-ext` を残したまま、ハンドル起点の派生方式 `sugiyama-port` を追加する

- **決定**: 整列アルゴリズムに `sugiyama-port`（`src/utils/sugiyamaPortLayout.ts`）を追加した。`sugiyama-ext`（方針E）のコピーを出発点に、**親子関係の決め方をハンドルの向き起点に置き換え**、**同順位の親を複数許し**、**cross群（上/下ハンドルの子）を親のすぐ隣に置いてforward群をprimary方向へ逃がす**ようにした派生方式。`sugiyama-ext` は比較対象としてそのまま残し、本番の既定も `sugiyama-ext` のまま変えていない（**改訂: 既定はのちに `sugiyama-port` へ移した。[§53](#53-本番の既定整列アルゴリズムを-sugiyama-ext-から-sugiyama-port-へ移す)**）。
- **背景**: `sugiyama-ext` の親選択は「その辺を採ったとき層が最も深くなる入辺」（ロンゲストパス）だけで決まる。これはハンドルの向きを見ないため、**ユーザーが「この向きに繋いだ＝これが親」と思って引いたエッジと、アルゴリズムが親とみなすエッジがずれる**ことがある。また、同じ深さの親が複数あっても先着1本に決め打ちするため、ダイヤモンド（`a→b→d` / `a→c→d`）で `d` が片方の親の真横に寄る。さらに、cross群をforward群の外側に逃がす設計のため、forward群が大きいほど「補足情報として付けた上/下の子」が親から遠ざかる。
- **採用理由**:
  - **親子関係はハンドルの向きから決まる、という規則のほうが操作に対して予測可能**。「ソース=右ハンドル → ターゲット=左ハンドル」が正規の親子関係だと決め、①ターゲットが入り口の面か ②ソースが出口の面か ③深さ（ロンゲストパス）の辞書式で選ぶ。深さは**同点を崩すためだけ**に降格した。
  - **同順位の親は捨てずに全部採る**ことで、「どちらが主たる親か」という本来存在しない区別を作らずに済む。複数親の子は親たちの最小共通祖先(LCA)の箱で、cross方向は全親のバリセンタ、primary方向は全親の要求を満たす最小位置に置く。
  - **補足情報（上/下ハンドルの子）は親の近くにあるほど関係が読める**。cross群を先に親の隣へ確保し、ぶつかったforward子は cross方向ではなく primary方向へ逃がす。cross方向に広げるとforward群（主線）の塊が崩れるため、**primary方向に伸びるほうを許容する**というトレードオフを明示的に採った。
  - `sugiyama-ext` を残したので、**同じ入力で並べて比較できる**（評価環境は8アルゴリズム総当たり）。定数もファイルも共有していないので、片方を消しても他方は壊れない。
- **測ってみた結果（採用時点で分かっている代償）**: 契約（ノード重なり0・ハンドル向き不一致0）は維持したが、**エッジ交差 2→27、エッジのノード貫通 46→97、描画面積 24813→36764千px²、平均移動量 164→240 と `sugiyama-ext` より悪い**（`ESCAPE_FORWARD_AS_GROUP=true` 時。`false` なら 19 / 105 / 28077 / 205）。兄弟順の反転率だけは 0.013→0.001 と良い。原因は構造的で、cross群が**親とforward子の間**に居座るため、逃がされたforward子へ引かれる直線がcross群の上を通る。**「補足情報を親の近くに置く」ことと「直線エッジが何も踏まない」ことは、ハンドル間を直線的なベジェで結ぶこの描画モデルでは両立しにくい**。どちらを取るかは数値では決まらないので、目視で判断する（コンタクトシート `npm run layout:sheet`）。
- **不採用案とその理由**:
  - **`sugiyama-ext` を直接書き換える**: 変更前後を並べて比較できなくなる。上記のとおりスコアには一長一短があり、**目視で選ぶ**必要があるため、両方が同時に存在することに意味がある（切り替えUIはdev限定で既にある）。
  - **複数親の扱いを `elk-port-pava` と同じ「層＋PAVA」にそっくり置き換える**: PAVAは層＝グローバルな一次元の並びを前提にする。方針E/Hの箱モデルは「サブツリーは剛体で兄弟サブツリー同士が入れ子にならない」ことで交差の少なさを担保しており（交差2件 vs `elk-port-pava` の209件）、層ベースにすると**この方式の最大の強みを失う**。そこでPAVAの考え方（希望位置＝全親のバリセンタ／制約を満たす最も近い位置へ置く）だけを箱モデルへ移植した。層ベースを試すなら `elk-port-pava` 側を方針E寄りに改造するほうが筋がよい。
  - **forward群を丸ごと同じ線に揃えて逃がす／cross方向で実際に重なる子だけ逃がす**: スコアは後者が全面的に良い（面積 36811→28077千px²・交差 26→19・移動量 241→205。「動かす必要のないものは動かさない」という差分レイアウトの方針（[§26](#26-整列は現在配置をヒントに使う差分的レイアウトelkのinteractive戦略)）とも整合する）が、**前者には「同じ層の兄弟のprimaryが揃う」という数値に出ない利点がある**。数値だけでは決められないため、どちらかを不採用にはせず `ESCAPE_FORWARD_AS_GROUP`（`sugiyamaPortLayout.ts` 冒頭。1行で切り替え）として残し、目視で決めることにした。**現在の既定は `true`（群ごと揃える）**で、これは目視評価のための一時的な設定。決めたらフラグを畳んで、選ばなかったほうのコードを消す。
  - **`CROSS_OVERLAP_RATIO` を下げて貫通を減らす**: 面積・移動量は改善するが**貫通は改善しない**（0.8→0 で貫通 105→112）。貫通の原因は被り量ではなく「cross群が親とforward子の間に居る」構造そのものなので、このつまみでは解けない。
- **実装で一度間違えた点（同じ轍を踏まないための記録）**: 複数親の子を**1つずつ独立に置くと壊れる**。同じ親の集合を持つ子は同じバリセンタを望むため、後から置く子が「cross方向で重なるものの前へ逃がす」規則に引っかかり、**並ぶべき兄弟がprimary方向へ1層ずつずれる**（`A→B,A→C` / `B→D,C→D` / `B→E,C→E` で `D` と `E` が前後になる）。**親の集合が同じ子は1つの群にまとめてcross方向に積み、押し出しの相手は群の外側だけにする**のが正しい。回帰テストは `e2e/branch-layout-algorithms.mjs` の31b。
- **再検討の条件**: 目視で `sugiyama-ext` / `sugiyama-port` のどちらかに決めたら、[align-branch-layout.md](./align-branch-layout.md)「今後の運び」に従って不採用側のファイル・切り替えUI・テスト・ドキュメントを削除する。貫通の多さが実用上気になる場合は、**cross群のサブツリーが深いときだけ方針E方式（cross方向へ逃がす）に切り替えるハイブリッド**が次の一手（「cross群は小さい補足情報」という前提が崩れたときだけ挙動を変える）。

## 50. `sugiyama-port` の上/下ハンドル子の置き場所は、ユーザーの現在位置から「補足情報か別の情報か」を読んで切り替える

- **決定**: `sugiyama-port`（方針H）で、cross群（上/下ハンドルの子。RIGHT時）の配置を2パターンに分け、**Align実行時点の現在位置から選ぶ**ようにした。判定は面ごと・バケット単位で、「そのバケットで**親にいちばん近い子**が、親自身とforward/backward群の**直接の子**が作る枠の内側にあるか」だけを見る。
  - 内側 → `hug`: 親のすぐ隣を確保し、forward群をprimary方向へ逃がす（[§49](#49-sugiyama-ext-を残したままハンドル起点の派生方式-sugiyama-port-を追加する) で入れた挙動）。
  - 外側 → `outside`: forward群の外側へ積む（＝`sugiyama-ext` と同じ扱い）。forward群は押さない。
  - 併せて被り量も2択にした（`CROSS_OVERLAP_RATIO_INSIDE`=0.2 / `CROSS_OVERLAP_RATIO`=0.8）。**forward群の帯に入り込む子だけ**深い被りを使う。
- **背景**: §49 の「cross群は親のすぐ隣」は、**cross群が親の補足情報である**という前提つきの扱い。前提が崩れて（cross群のサブツリーが大きい）と、forward群＝主線を延々とprimary方向へ押し出し、流れを阻害する。前提が成り立つかは構造からは判定できない。
- **採用理由**:
  - **前提が成り立つかは「ユーザーがどこに置いたか」に表れている**。親のすぐ横に添えてあるなら補足情報、主線の外側に離して置いてあるなら独立した枝、と読むのが自然で、ユーザーの操作に対して予測可能。
  - **新しい種類の入力を持ち込んでいない**。現在位置をヒントに使う差分レイアウト（[§26](#26-整列は現在配置をヒントに使う差分的レイアウトelkのinteractive戦略)）の延長で、兄弟の並び順・rootのアンカーを現在位置から取るのと同じ仕組み。特定のグラフ形に条件を足す（＝個別例へのオーバーフィット）のではなく、**両極の扱いを既存の2方式（方針E / 方針H）から取り、その間の選択だけを位置に委ねている**。
  - 実測でも改善した（43ケース＋規模ケース、`ESCAPE_FORWARD_AS_GROUP=true`）。**面積 36764→31078千px²、エッジ交差 27→20、貫通 97→85、平均移動量 240→191**。契約（重なり0・ハンドル向き不一致0）は維持。`sugiyama-ext` との差の半分近くを取り戻し、**充填率 0.469 は全8方式で最良**になった。
- **判定が揺れないことを設計条件にした**: 判定材料が「整列で自分が動かす対象」なので、素朴に作ると整列後の位置が別パターンに分類され、**Alignを押すたびに2つの配置を往復する**。次の2点で防いでいる（回帰テストは `e2e/branch-layout-algorithms.mjs` の32b）。
  - **見るのは「親にいちばん近い子」だけ**。2番目以降の子は1番目の外側に積まれるので、全員を見ると整列後に必ず「外側」判定になる。
  - **判定が本質的に曖昧なケース（forward群が親より小さいとき）は、両パターンの出力を一致させる**。このとき2パターンのcross方向の結果は同じで違いは被り量だけなので、「押し出しが起きない子には深い被りを使わない」という規則によって被り量も一致する＝分類がどちらに転んでも同じ絵になる。
- **不採用案とその理由**:
  - **構造（cross群のサブツリーの大きさ・深さ）で切り替える**: 「ユーザーが親の隣に置いたのに勝手に外へ出る」ことになり、操作に対する予測可能性を失う。しきい値も恣意的になる（何ノードから「大きい」のか）。現在位置の判定より優先させてはいけない。
  - **子ごとにパターンを決める**（バケット単位ではなく）: より細かく効くが、整列後は2番目以降の子が1番目の外側に積まれるため判定が反転し、Alignの反復で往復する。バケット単位＋「いちばん近い子」だと整列後も同じ分類になる。
  - **被り量を一律に下げる（`CROSS_OVERLAP_RATIO` = 0.2 固定）**: primary方向の伸びは抑えられるが、**エッジのノード貫通は改善しない**（0.8→0 で 105→112 と微増。貫通の原因は被り量ではなく「cross群が親とforward子の間に居る」構造）。かつ、押し出しが起きない子の見た目まで変えてしまい、上記の「曖昧なケースで両パターンを一致させる」性質も失う。
  - **判定にヒステリシス（前回の分類を保存する）を持たせる**: 往復は防げるが、分類という状態をノードごとに永続化することになり、ストレージのスキーマ変更と「整列結果が保存状態に依存する」不透明さを招く。出力が自分の判定を保つように作れば状態は不要。
- **実装で一度踏んだ罠**: `outside` のcross群を「複数親の子」より**後**に置くと、outside群のサブツリーに親がいる子がアンカーを見つけられず、**座標が返らないまま初期位置に取り残されて他のノードと重なる**（`finalTopLeft.get(id) || n.position` のフォールバックが効くため、MISSING_NODE ではなく node-overlap として現れる）。ファズ（seed=48、22ノード）で検出。**箱に属するノードは「複数親の子」の手順より前に全部置き終わっていること**が必要。回帰テストは `e2e/branch-layout-algorithms.mjs` の32c。

## 51. ハンドルドラッグ終了時の「空白ドロップ判定」はDOMヒットテストではなくReact Flowの`connectionState`で行う

- **決定**: `onConnectEnd`（`src/components/Editor/MindMapCanvas.tsx`）で、React Flowが渡してくる第2引数 `connectionState` の **`toHandle` が非nullなら新規ノード作成を打ち切る**ようにした。従来の `document.elementFromPoint` によるDOMヒットテスト（ペイン上か／ノード上か）は、その後の判定としてそのまま残している。
- **背景（不具合）**: 「ハンドルからドラッグして既存ノードのハンドルに接続すると、エッジは正しくできるのに、同時に新規ノードも作られることがある」。React Flowは `connectionRadius`（既定20 flow単位。このアプリでは指定していないので既定値）以内でドロップすると最近傍ハンドルへ**スナップして接続を成立させる**（`onConnect`が発火する）。ハンドルはノード枠上に12px四方で描かれるため外側へ6px程度しかはみ出しておらず、**スナップは成立するがポインタ自体はノードDOMの外＝ペイン上にある領域**が存在する。この領域で離すと、DOMヒットテストは「空白へのドロップ」と判定して新規ノードを作り、React Flow側は接続を成立させる。結果としてエッジ接続と新規ノード作成が同時に起きる。「たまに起きる」「離すタイミングの問題に見える」のは、ドロップ位置の精度で入るかどうかが変わるため。
- **採用理由**:
  - **接続が成立したかどうかを知っているのはReact Flow自身**なので、その状態を直接読むのが正しい。DOMヒットテストは「ポインタの真下に何があるか」しか答えられず、**スナップという座標ベースの挙動を再現できない**（半径・ズーム倍率・最近傍選択のロジックを自前で複製することになる）。
  - `isValid` ではなく **`toHandle` を見る**。`toHandle` は「スナップ先ハンドルが見つかった」時点でセットされ、接続が無効だった場合（同一ハンドルへ戻した等）も入る。無効でも**ユーザーは既存ハンドルを狙っていた**のだから、その場に新規ノードを作らないほうが意図に沿う。従来もハンドル直上へのドロップはDOMヒットテストで弾いていたので、挙動の一貫性も保てる。
  - React Flow v12公式の「エッジドロップでノードを追加する」例と同じ経路（`onConnectEnd(event, connectionState)`）に乗る。v12で第2引数が追加されているのに使っていなかった、というのが実態。
- **不採用案とその理由**:
  - **`onConnect` が発火したことをrefに記録し、`onConnectEnd` で見て打ち切る**: 動くが、`onConnect`→`onConnectEnd` の発火順序（React Flow内部の実装順）に暗黙に依存する。`connectionState` は同じ情報を**引数として明示的に**渡してくるので、順序への依存が要らない。
  - **`connectionRadius` を0か極小にしてスナップ自体を無効化する**: スナップはハンドルへの接続を楽にする機能で、特にタッチ環境では効果が大きい。**不具合の原因ではなく便利機能のほうを削る**ことになるので採らない。
  - **DOMヒットテストの判定範囲をハンドル周辺へ広げる（ノード矩形をNpx膨らませる等）**: `connectionRadius`はflow座標なので、画面上の許容距離はズーム倍率で変わる。自前で追従させると**React Flow側の実装と二重管理になり、ズーム時にずれる**。
- **再検討の条件**: React Flowが `connectionState` の形（`toHandle`/`isValid`）を変えた場合。また、「ハンドルのすぐ外側で離したときは新規ノードを作りたい」という要望が出た場合は、`toHandle` ではなく `isValid === true`（＝実際に接続が成立したときだけ打ち切る）に緩める。
- **回帰テスト**: `e2e/edge-drop-connect.mjs`（[testing.md](./testing.md)）。ドロップ点がノードDOMの外側であることを前提としてアサートしてから実行するため、条件が崩れて「常にPASSするテスト」にはならない。

## 52. ハンドルドラッグで作る新規ノードは、引き伸ばし始めた面がbackwardなら「受け口も位置もforward面基準」にする

- **決定**: `onConnectEnd`（`src/components/Editor/MindMapCanvas.tsx`）で空白ドロップから新規ノードを作るとき、**ドラッグ開始ハンドルの面**に応じて2つを切り替える。
  - **受け口**（新規ノード側の `targetHandle`）: 開始面が **backward**（RIGHT:`left` / DOWN:`top`）のときだけ **forward 面**（RIGHT:`right` / DOWN:`bottom`）。それ以外（forward 面・cross 面 = RIGHT の `top`/`bottom`）は従来どおり **backward 面**。
  - **位置**: React Flowの位置は左上基準なので、ドロップ点はそのままだと常に新規ノードの backward 面（RIGHT:左端 / DOWN:上端）になる。**開始面が backward のときは primary 方向へ1ノード分ずらし、ドロップ点が forward 面（RIGHT:右端 / DOWN:下端）になるようにする**。ずらし量は空ノードの実寸定数 `EMPTY_NODE_WIDTH` / `EMPTY_NODE_HEIGHT`（`src/utils/nodeContent.ts`）。
- **背景**: 従来は開始ハンドルに関係なく `targetHandle` を backward 面に固定し、位置もドロップ点＝左上に固定していた。右向きレイアウトで**左ハンドルから左方向へ引き伸ばす**と、(1) エッジが親の左から出て新規ノードの左に入る＝**新規ノードを回り込んで折り返す**線になり、(2) 新規ノードが**ポインタの右側＝親の側へ伸びる**ので、引き伸ばした向きと逆に生える見た目になっていた。整列（`sugiyama-ext` 系）は「ソース面が backward なら子を1層後退させる」と解釈するため、線の形・位置・階層の解釈が三者で食い違っていた。
- **採用理由**:
  - **受け口**: `targetHandle` 未指定時にレイアウト側が推定する既定と一致する。`sugiyamaPortLayout.ts` の `targetSideOf` / `elkPortLayout.ts` は「`targetHandle` が無ければソース面の反対面」とみなす。backward 起点なら反対面＝forward 面なので、明示した値が推定値と同じになり、方式間で解釈が割れない。
  - **位置**: 「ポインタは常に**エッジが入ってくる面**」という規則に揃う。ドラッグは「引き伸ばした先にノードが生える」操作なので、ポインタの奥側（引き伸ばした向き）へノードが伸びるほうが直感に合う。
  - cross 面（RIGHT の上/下ハンドル）を対象にしないのは、cross 起点の子は**同じ層かおよそ半層先**に置かれる扱い（`roleDelta`＝0.5）で、流れ方向としては前進しているため。上/下から出て backward 面で受け、ドロップ点が左上のままでよい。
- **不採用案とその理由**:
  - **常に「ソース面の反対面」で受ける**（`{left↔right, top↔bottom}` の機械的な反転）: cross 起点でも `bottom`→`top` になり、右向きレイアウトで**上下に並ぶ子の受け口が縦向き**になる。既存データ（`e2e/lib/layout-cases.mjs` の `oppositeSide`）はこの規則だが、手作りのケース生成と実操作で作るデータを同じにする必要はない。実操作では「上/下から出た子も左で受ける」ほうが整列後の線が素直。
  - **開始ハンドルに関係なく forward 面で受ける／常にポインタを右端にする**: forward 起点（右ハンドル→右へ伸ばす）で線が折り返し、ノードもポインタの手前に生えてしまう。いちばん多い操作が悪化する。
  - **ずらし量に `DEFAULT_NODE_WIDTH`(180)/`DEFAULT_NODE_HEIGHT`(60) を使う**: あちらは「サイズ不明なノードの代表値」で、空ノードの実寸（150×44）とは30px/16px ずれる。ポインタとノード端の間に見える隙間になるので、**空ノード専用の実寸定数を別に持つ**ことにした（`EMPTY_NODE_WIDTH`/`EMPTY_NODE_HEIGHT`。`CustomNode` の `min-w-[150px]` と1行ぶんの高さで決まる値）。
  - **作成後にReact Flowの実測（`node.measured`）を待ってから位置を補正する**: 実寸に完全追従できるが、**作成直後にノードが1フレーム分ジャンプする**うえ、編集モードへ入る処理（armed-focus）と同じタイミングで位置更新を挟むことになる。空ノードの寸法は定数で決まるので、複雑さに見合わない。
- **再検討の条件**: `CustomNode` の最小幅・パディング・行高を変えたとき（`EMPTY_NODE_WIDTH`/`EMPTY_NODE_HEIGHT` を測り直す。回帰テストが検出する）。整列方式が「ターゲット面」をもっと強く見るようになった場合（例: cross 起点でも受け口の向きで層を変える）は cross 起点の扱いも見直す。
- **回帰テスト**: `e2e/edge-drop-handle-side.mjs`（[testing.md](./testing.md)）。RIGHT の4面＋DOWN の3面から引き伸ばし、`sourceHandle`/`targetHandle` の組み合わせと「ドロップ点が新規ノードのどの面になるか」を固定する。受け口を backward 固定に戻す・位置のずらしを外す（RIGHT/DOWN それぞれ）の3通りで実際に FAIL することを確認済み。

## 53. 本番の既定整列アルゴリズムを `sugiyama-ext` から `sugiyama-port` へ移す

- **決定**: 本番ビルドの既定整列アルゴリズム（`src/hooks/useAlignAlgorithmDebug.ts` の `DEFAULT_ALGORITHM`）を `sugiyama-ext` から **`sugiyama-port`** に変更した（[§49](#49-sugiyama-ext-を残したままハンドル起点の派生方式-sugiyama-port-を追加する) の暫定状態からの昇格）。dev限定の比較切り替えUIと他候補（`uniform`/`branch`/`flat-axis`/`sugiyama-ext`/`elk-port`/`elk-port-ext`/`elk-port-pava`）のコードは**まだ削除していない**。
- **背景**: [§49](#49-sugiyama-ext-を残したままハンドル起点の派生方式-sugiyama-port-を追加する) で「スコアでは決まらないので目視で決める」としていた `sugiyama-ext` / `sugiyama-port` の選択を、実際に触って比較した結果 `sugiyama-port` に決めた（ユーザー判断）。
- **採用理由**: `sugiyama-port` の設計（親はハンドルの向きで決める／同順位の親を複数許す／cross群は親のすぐ隣に置く。[§49](#49-sugiyama-ext-を残したままハンドル起点の派生方式-sugiyama-port-を追加する)・[§50](#50-sugiyama-port-の上下ハンドル子の置き場所はユーザーの現在位置から補足情報か別の情報かを読んで切り替える)）が、**「この向きに繋いだ＝これが親」という操作の意図と整列結果を一致させる**という当初の目的に対してそのまま効く。§49 で測った代償（エッジ交差 2→27・貫通 46→97・面積 24813→36764千px²・平均移動量 164→240）は**既知のまま受け入れる**判断で、目視での読みやすさを優先した。
- **この変更で本番挙動に載るもの（暫定設定だったものの昇格）**:
  - `ESCAPE_FORWARD_AS_GROUP = true`（`src/utils/sugiyamaPortLayout.ts` 冒頭）。「forward群を丸ごと同じ線に揃えて逃がす」側。[§49](#49-sugiyama-ext-を残したままハンドル起点の派生方式-sugiyama-port-を追加する) では目視評価のための一時設定としていたが、既定が `sugiyama-port` になった以上**これが本番の挙動**になる。フラグを畳む（選ばなかったほうのコードを消す）のは未実施。
  - [§50](#50-sugiyama-port-の上下ハンドル子の置き場所はユーザーの現在位置から補足情報か別の情報かを読んで切り替える) の hug / outside 判定（現在位置からバケット単位で選ぶ）も同様に本番挙動になる。
- **不採用案とその理由**:
  - **スコアが `sugiyama-ext` に並ぶまで既定を移さない**: 交差・貫通の悪化は「cross群が親とforward子の間に居る」という構造由来で、つまみで解けないことは §49 で確認済み（`CROSS_OVERLAP_RATIO` を下げても貫通は改善しない）。数値が並ぶのを待つと永久に移せない。
  - **既定を移すのと同時に `sugiyama-ext` と比較UIを削除する**: 既定を本番で使い込んだ結果ひっくり返る可能性が残っており、その時に並べて見比べられる状態を保っておきたい。削除は[align-branch-layout.md](./align-branch-layout.md)「今後の運び」の手順で別途行う（`sugiyamaExtLayout.ts` は定数を `useNodeCreation.ts` へ提供しているため、消すなら定数の移設が要る）。
- **再検討の条件**: 実使用で貫通・交差の多さが気になる場合は、§49 の「cross群のサブツリーが深いときだけ方針E方式（cross方向へ逃がす）に切り替えるハイブリッド」が次の一手。既定を `sugiyama-ext` に戻すだけなら `DEFAULT_ALGORITHM` の1行を書き換えるだけで済む（他候補のコードを残しているのはこのため）。既定として十分に使い込んで確定したら、不採用側のファイル・切り替えUI・関連テスト・ドキュメントを削除する。

## 54. ノードのコンテキストメニューに「サブツリーを選択」を追加し、選択は `setMultiSelection` に載せる

- **決定**: ノードの右クリック / 長押しメニュー（[§47](#47-ノードのコンテキストメニューは対象のdom矩形anchorrectを基準に自己サイズ計測して配置する)）に、削除の上に**「サブツリーを選択」**（`contextMenu.selectSubtree`）を追加した。押すと「対象ノード自身＋`getDescendantIds()` でたどれる全子孫」を `uiStore.setMultiSelection()` で一括選択し、メニューを閉じる。エッジのメニューには出さない（サブツリーの起点はノードにしか無いため）。
- **背景**: 枝ごとの一括操作（まとめて削除する・その枝だけ整列する・まとめて動かす）に、これまでは `Ctrl`+クリックの1個ずつのトグルか、`Shift`+クリックの経路追加（[§36](#36-複数選択-ctrl単体トグル追加shiftアンカーからの無向最短経路をunion追加)相当）しか無く、枝が深いほど操作数が増えていた。「この枝を丸ごと」という単位はDAGでも一意に決まる（子方向の到達可能集合）ので、メニュー1項目で出せる。
- **採用理由（実装上の選択）**:
  - **子孫の探索は既存の `getDescendantIds()`（`src/utils/graphTraversal.ts`）を使う**。子方向DFS＋訪問済み集合なので、このアプリが許している循環エッジ（[§26](#26-整列は現在配置をヒントに使う差分的レイアウトelkのinteractive戦略)の「循環エッジの向きを保つ」仕様）があっても止まる。`useNodeCreation.ts` のサブツリー移動と同じ「サブツリー」の定義になるので、ユーザーから見た枝の範囲が操作をまたいで一致する。
  - **選択の反映は `setMultiSelection()`**。矩形選択（`onSelectionChange`）と同じ経路に載るので、複数選択の不変条件（`selectedNodeId` をクリアする・編集中ノードが選択から外れたら編集を終了する。[§27](#27-編集中ノードは常に選択中の不変条件を選択セッターで強制する)）を再実装せずに満たせる。結果として、選択後は `Delete` の一括削除も選択範囲だけの整列（`Ctrl+Shift+L`）もそのまま効く。
  - **`setMultiSelection()` の前に `clearEdgeSelection()` を呼ぶ**。`setMultiSelection()` はノード・エッジ混在選択のために `selectedEdgeIds` を維持する仕様なので、呼ばないと「直前に選択していた無関係なエッジ」が残り、続けて `Delete` を押すとサブツリー外のエッジまで消える。「サブツリーを選択」の結果は**そのサブツリーちょうど**であるべき、という一貫性を優先した。
- **不採用案とその理由**:
  - **サブツリー内のエッジも一緒に選択する**: ノードを消せば接続エッジは連鎖して消えるので削除用途では不要。一方で「エッジも選択中」の見た目（ハイライト）が増えると、何が選ばれているかが読みにくくなる。必要になったら足せる（選択集合の両端がサブツリー内のエッジ、が定義になる）。
  - **子孫が無いノードでは項目を隠す/無効化する**: 「押しても自分1個が選ばれるだけ」で害が無く、メニューの項目数が対象によって変わるほうが操作の予測を乱す（位置が動いて誤タップの原因になる）。常に出す。
  - **キーボードショートカットも同時に割り当てる**: 空きキーの選定と[ヘルプ](../src/components/Common/HelpModal.tsx)への反映が要るうえ、まず「メニューから使えること」で十分という判断。要望が出たら追加する。
  - **無向（親方向にもたどる）連結成分を選ぶ**: それは「サブツリー」ではなく「つながっている塊全部」で、ルート付近を対象にすると事実上の全選択になる。`Shift`+クリックの経路追加と役割も被る。
- **再検討の条件**: 「親も含めて枝ごと」「兄弟だけ」といった別の選択単位の要望が出たら、メニューをサブメニュー化するか、選択系の操作をまとめた別UIに移すことを検討する（今は項目2つなのでフラットで足りる）。
- **回帰テスト**: `e2e/context-menu-select-subtree.mjs`（[testing.md](./testing.md)）。エッジの `aria-label` からテスト側でグラフを組み直して期待値を独立に計算し、サブツリー内が全部選択・サブツリー外が非選択であること、続く `Delete` でサブツリーだけが消えること、エッジのメニューには項目が出ないことを確認する。メニュー項目を消した状態で実際に FAIL することを確認済み。

## 55. 利用規約・プライバシーポリシーは `public/` の素の静的HTML（英日併記）に置く

- **決定**: 利用規約とプライバシーポリシーを [public/terms.html](../public/terms.html) / [public/privacy.html](../public/privacy.html) として、React アプリとは独立した素の静的HTML（インラインCSS・JS不使用）で用意し、`https://mu-777.github.io/MindMeshMap/terms.html` / `.../privacy.html` で配信する。1ファイル内に**英語→日本語の順**で全文を併記し、日本語版を正文とする。アプリ内の導線はサイドバー下部（Googleログインボタンの下）に `legal.terms` / `legal.privacy` の小さなリンクを置き、`index.html` の `<noscript>` にも同じリンクを入れる。連絡先は `mu777.labs@gmail.com`、準拠法は日本法・東京地方裁判所の専属的合意管轄。
- **背景**: Google API（Drive API + Google Identity Services）を使うには、Google Cloud Console のブランディング設定に「アプリのホームページ」「プライバシーポリシー」「利用規約」の**URL**を登録する必要がある。登録するURLは、ログインなしで公開されていること・ホームページと同一ドメイン（承認済みドメイン `mu-777.github.io`）にあること・審査側が確実に読めることが求められる。
- **採用理由**:
  - **`public/` 配下なら Vite が dist へそのままコピーし、GitHub Pages がそのまま配信する**。ビルド設定もルーティングも追加不要で、バックエンドなし・ランニングコストゼロの方針（[CLAUDE.md](../CLAUDE.md)）に一切触れない。
  - **JS を実行しないクローラ・審査ツールでも全文が読める**。アプリ本体は `#root` にJSで描画されるためDOMに文字が残らない（[§28](#28-seo検索順位対策-メタ強化構造化データsitemaprobotsnoscriptフォールバック) と同じ問題）が、この2枚は素のHTMLなので影響を受けない。
  - **英日を1ファイルに併記する**のは、Console に登録するURLが1つで済み、審査担当者が読む英語が必ず先頭に来るため。言語別ファイルにすると、テストで守れない場所に「片方だけ更新して放置」という i18n 同期事故を持ち込むことになる。
  - **中国語は用意しない**。UI は en/ja/zh の3言語だが、法的文書は訳の正確性を開発者が検証できない言語で出すべきではないという判断（zh UI からのリンクラベルだけ `legal.*` に3言語分揃え、リンク先は英日併記のページ）。
- **不採用案とその理由**:
  - **SPA 内のルート（`/privacy` 等）にする**: GitHub Pages は deep link を 404 にするため `404.html` へのフォールバックが必要になる。審査の入口が壊れると致命的で、JS必須という弱点も残る。
  - **アプリ内モーダル（[KeyboardShortcutHelp](../src/components/Common/KeyboardShortcutHelp.tsx) と同様）だけにする**: URL が無いので Console に登録できない。導線としては有効なので、将来足すとしても静的HTMLの置き換えではなく追加になる。
  - **リポジトリの Markdown / GitHub Wiki を指す**: `github.com` は自分の承認済みドメインではなく、ホームページと別ドメインになるため要件を満たさない。
  - **`vite.config.ts` の `rollupOptions.input` にHTMLエントリを追加する（マルチページビルド）**: 動くが、ポリシー文書に React も TS もバンドルも要らない。ビルド構成を複雑にする対価が無い。
  - **i18next のリソース（`src/locales/*.json`）に全文を入れる**: 長文の法的文書をJSON文字列で持つのは差分が読めず、上記の「JS必須」問題も解決しない。
- **Google Cloud Console 側の前提（コードでは担保できない運用事項）**:
  - 承認済みドメインは `mu-777.github.io`（`github.io` は Public Suffix なのでこのホストが登録単位）。所有権確認は `index.html` に既に入っている `google-site-verification` メタタグ経由の Search Console 確認で満たせる。
  - 現在のスコープ（`drive.file` / `openid` / `userinfo.email` / `userinfo.profile`）は**すべて非センシティブ**のため、OAuth アプリ審査は不要。公開ステータスは「テスト」のままだとトークンが7日で失効しテストユーザー100人の上限があるので「本番」にする。
  - **アプリのロゴを登録するとブランド確認の審査が走る**ため、必要になるまでロゴは空のままにする。
- **同期が必要な箇所（片方だけ直さないこと）**: 発効日・連絡先・準拠法は `terms.html` と `privacy.html` の両方にある。プライバシーポリシーのストレージキー表は [tuning.md](./tuning.md)「ストレージキー」と、OAuth スコープの説明は [useGoogleAuth.ts](../src/hooks/useGoogleAuth.ts) の `SCOPES` と一致させる。ページを増やしたら [public/sitemap.xml](../public/sitemap.xml) にも追加する。
- **再検討の条件**: センシティブ／制限付きスコープ（例: `drive` 全体）を要求するようになったら OAuth 審査が必須になり、ポリシーの記載内容にも追加要件（データ取り扱いの詳細・デモ動画等）が生じるため、この項を改訂する。独自ドメインへ移行する場合も承認済みドメインとポリシーURLの更新が要る。
